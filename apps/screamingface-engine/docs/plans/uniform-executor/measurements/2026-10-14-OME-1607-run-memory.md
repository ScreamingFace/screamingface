# Run memory of a judged benchmark, before and after OME-1607 (2026-10-14)

Refs: OME-1607 (under OME-1314). Spec: `docs/spec/2026-10-14-OME-1607-run-scheduling-memory.md`.

## Method

- Local kind cluster `sf-prod` on Colima (6 vCPU, 10 GiB VM), runner pool 2 pods × 2 slots,
  chart defaults otherwise (`perRunCharge.memoryLimitMi` 1024). aigateway with the dev response
  cache snapshot loaded (467,895 rows).
- Workload: `draco-3pass`, 100 Cases, one Candidate (`claude-fable-5`), replayed from a recorded
  URL4 run through a KEYLESS identity — every call is a cache hit, so a miss fails instead of
  spending. ~7,400 judge calls (`gemini-3.1-pro-preview`) in the aggregate.
- Per child process, every second: `VmRSS`, `VmSize` from `/proc/<pid>/status`; per pod:
  `/sys/fs/cgroup/memory.current`. Attribution with `mallinfo2`, `gc.get_objects()` type counts and
  `gc.get_referrers` chains from a `sitecustomize` hook (diagnostic only, removed after).

## Results

| Build | Run start VSZ | Peak RSS | Peak VSZ | Growth | Outcome |
|---|---|---|---|---|---|
| main (`9be66ecb0`) | 1,884 MiB at +6 s | 459 MiB | 2,045 MiB | ~4 MiB/s, linear | `MemoryError` at the 2 GiB `RLIMIT_AS` |
| main + runner env only (experiment) | 660 MiB | ~550 MiB | ~915 MiB | ~4 MiB/s, linear | succeeded |
| OME-1607 branch (chart defaults) | 672 MiB | 444 MiB | 849 MiB | ~1.3 MiB/s | succeeded in 71.7 s |

Full load on the OME-1607 build (an owner evaluation of 7 Candidates, 4 runs at once filling all
slots): each run child 300–463 MiB resident; each pod's cgroup 756–787 MiB of its 2,304 MiB limit.
3 runs succeeded, 4 were cancelled by the owner; no memory stop, no restart.

## What the numbers say

- The jump at run start was address space reserved by native libraries: pyarrow's default pool
  (mimalloc) reserves a 1 GiB arena on its first allocation; numpy/OpenBLAS ~32 MiB per node CPU.
  The runner env (`ARROW_DEFAULT_MEMORY_POOL=system`, one BLAS/OpenMP thread) removes both.
- The linear growth was live memory (glibc in-use 107 → 226 MiB; free-but-held stayed 5–30 MiB;
  glibc tuning did not change the slope): one inspect `ModelEvent` per judge call, kept by the
  Transcript in each finished Case task's context, kept by the aggregate's task list.
- What still grows with calls (~1.3 MiB/s here) includes the cost-attribution ledger, measured at
  2.8 KB per call (27 MiB per 10,000 calls) — accepted, see the plan §6.
- With the default 1 GiB per-slot resident budget, `draco-3pass` peaks at ~45% of its budget.
  `draco` (5 passes, ~12,000 judge calls) was not replayed (passes 4–5 are not cached, so a replay
  would spend); extrapolating the remaining slope gives roughly 500–550 MiB.

## Not measured

- A multi-attempt board (`arc_agi_2`) and an `early_result` board (IFEval, HealthBench): their
  Candidate answers are not in the cache, so a run would spend.
- Prod node sizes: the OpenBLAS reservation scales with CPUs; the env removes it regardless.
