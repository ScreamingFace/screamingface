# CyberMetric-500 — Fidelity Record

## Verdict

**`unverified`.** Our headline is plain accuracy over the 500 CyberMetric-500 questions. It is built to sit beside a run of [inspect_evals v0.20.0 `cybermetric_500`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric), which uses a system message, the default `multiple_choice()` template, the `choice()` scorer and the `accuracy` metric. inspect_evals publishes no number for this eval. Our headline is **not** comparable to the paper's Table III (GPT-4o 93.40% on 500 Q; [Tihanyi et al. 2024, v2](https://arxiv.org/abs/2402.07688v2)), which is also the row's Frontier Score. The reason is that inspect_evals marks a different exam from the authors' harness. First, it pins the December 2024 data file, while the paper's June 2024 numbers came from the February 2024 file, and 137 of the 500 Cases differ between the two (`137/500 = 0.274`). Second, it asks with a different prompt. Third, it extracts the answer differently: the harness takes the first case-insensitive `ANSWER:?\s*[A-D]` anywhere in the reply and re-asks up to five times when that fails. Together these are `unbounded` (Upstream notes). Against inspect_evals, three things hold. (1) Every Case is served with inspect's exact text, key and options. (2) Our 8,500 sheet marks equal inspect's own solver and scorer on every sheet. (3) The roll-up equals inspect's to four decimals on eight vectors. One deviation remains, and it is undeclared: D1, the system message delivered as leading user text. It is `possibly-score-changing` with bound `unknown`. Arithmetic: `bounds against inspect_evals = unknown (D1)`. One `possibly-score-changing` deviation is open, so the rule gives `unverified`. Once D1 is bounded at ≤ 0.005, the rule gives `comparable-to-inspect`, because inspect_evals vs the original harness is `unbounded` (with a lower bound of 137/500 = 0.274 from the data alone).

## Deviations

### D1 — the eval's system message rides inside the user prompt

- **Undeclared on the row.** The row carries no `# NAMED DEVIATION` line (`awk` over `apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2923-2983` and `prepare.py:389-400` found none, Checks run 7). It has no `named_deviations/` scorer, no `dropped_scorers` and no `excluded_sample_ids` (`None`, Checks run 2), and no linked README. The Task-replay spec's D3 names only musr and xstest (`docs/spec/2026-10-02-ome-1460-one-fetch-path.md:259-262`, `:283`; `grep -n cybermetric` there → no line). Two things come close. The row's description says the questions are "asked with the eval's own system message" (`benchmarks.py:2928-2929`), but does not say the message arrives as user text. The plugin-wide comment at `capture.py:75-77` calls the fold a "Named deviation (contracteval pattern)", and the glossary lists "a system message delivered as input text" as an example (`CONTEXT.md:323-326`). Neither is one of the declaration forms the rule accepts, so this is a finding. Either form would make it declared. It would still be counted the same way.
- **Where.** Ours: `SYSTEM_MESSAGE + "\n\n" + user prompt` as one user text (`apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:79`, `:530-538`). The grader gets that single user message (`scorer_adapter.py:635`). Theirs: `system_message(SYSTEM_MESSAGE)` inserts a `ChatMessageSystem` before the user turn (`inspect_evals:cybermetric/cybermetric.py:35`, `:77`; `inspect_ai:solver/_prompt.py:46-70`). The original harness also sends `{"role": "system"}` then user (`fork:CyberMetric_evaluator.py:31-34`).
- **What differs.** Every byte of text is equal on all 500 Cases (Checks run 4). The Candidate receives "You are a security expert who answers questions." as the opening of the user turn, not as a system turn. The scorer never reads it, since `choice()` reads only the reply and the choices.
- **Severity / bound.** `possibly-score-changing`, `unknown`. A Candidate may follow a system instruction differently from user text. This needs a paired Candidate run over the 500 Cases (Recommended paid runs).

## Recommended paid runs

- **D1, system turn vs folded text (bounds the open deviation).** Use one Candidate on all 500 Cases with no judge, since the scorer is deterministic.
  - **Arm A:** inspect's own `eval()` of `cybermetric_500()` (system message as a system turn).
  - **Arm B:** our served Case input as one user message.
  - **Noise floor:** run each arm twice, or fix `temperature=0` where the Candidate allows it. The paper reports 3–4 pp run-to-run variation at temperature 1.0, so the floor matters here.
  - **Readout:** compare per-Case marks and the headline difference. If |A − B| ≤ 0.005 beyond the noise floor, D1's bound is that difference and the rule gives `comparable-to-inspect`.
  - **Cost:** Candidate tokens only, about 150 input tokens and a few output tokens per Case per sitting, so roughly 4 × 500 short calls.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `cybermetric`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric) keeps the harness's system message and its `Question: …\nOptions: A) …, B) …` rendering (`cybermetric.py:35`, `:115-116`; `fork:CyberMetric_evaluator.py:25-26`, `:32`). It changes the rest of the exam [cybermetric/CyberMetric@7c565c65](https://github.com/cybermetric/CyberMetric/tree/7c565c65c03ac5bb06b1f94da410cd3f9b91dafe) gave.
  1. **Data, 137/500 = 0.274.** inspect_evals pins `205262cd` (2024-12-18, `cybermetric.py:31-32`). That commit comes after the dataset fixes `62cc8a9` (2024-12-11), `01ee939`, `ec88fb3` and `205262cd`. The paper's v2 (3 Jun 2024) numbers came from the February 2024 file (`47b6443`, unchanged until December). Matching by exact question text: 57 pin questions are new, 78 have changed options and 2 have a changed key. That makes 137 Cases where the pin's exam differs from the paper's. The pin also rebalances the keys to 125 per letter, where the paper-time file had A 129 / B 116 / C 127 / D 128.
  2. **Prompt.** The harness's user turn ends `Choose the correct answer (A, B, C, or D) only. Always return in this format: 'ANSWER: X' ` (`fork:CyberMetric_evaluator.py:26`). inspect wraps the same question in its `SINGLE_ANSWER_TEMPLATE` (`inspect_ai:solver/_multiple_choice.py:17-23`). Because `record_to_sample` sets `choices` to the option *letters* (`cybermetric.py:119`), inspect then appends a second option list that reads `A) A`, `B) B`, `C) C`, `D) D` (`inspect_ai:solver/_multiple_choice.py:57-68`). The real option texts appear only in the comma-joined `Options:` line. See Case 1 in Checks run 4.
  3. **Answer extraction.** The harness takes the **first** case-insensitive `ANSWER:?\s*([A-D])` anywhere in the reply (`fork:CyberMetric_evaluator.py:19`). The colon is optional, and the regex reads the first letter of the following word, so "answer depends" gives D and "answer choice" gives C. inspect takes the **last** `ANSWER\s*:` line, requires the colon and a lone allowed letter (`inspect_ai:solver/_multiple_choice.py:98-121`, `:147-150`). On the sheets they disagree on 500/500 Cases for four reply shapes and on 375/500 for a fifth (Checks run 4).
  4. **Retries.** The harness re-asks the model up to five times when the reply has no parseable letter (`fork:CyberMetric_evaluator.py:24`, `:27-45`), so a format slip costs nothing unless it repeats. inspect asks once and marks an unparseable reply wrong.

  The gap from items 2–4 depends on how a Candidate writes its reply, so it cannot be bounded without a run. Item 1 alone exceeds tolerance. Hence the verdict is at best `comparable-to-inspect`, never `comparable-to-paper`.
- **Harness vs paper: sampling settings.** The paper states "temperature of 1.0, top_p at 0.9, and top_k at 50" for its AWS-hosted models (§IV-A). The published evaluator hard-codes `model="gpt-3.5-turbo-0125"` with no sampling arguments, so it uses the API defaults (`fork:CyberMetric_evaluator.py:29-35`). The paper also warns of 3–4 pp variation between runs. The harness wins, and the difference is recorded, not counted.
- **The data file moved again after inspect's pin.** `086409d` (2026-05-27) changed 7 of the 500 rows relative to `205262cd` (positions 23, 45, 77, 101, 160, 344, 416, two with a new key). Neither inspect_evals v0.20.0 nor we read it. Bound 0 for this record. A future inspect_evals pin bump would change those Cases.
