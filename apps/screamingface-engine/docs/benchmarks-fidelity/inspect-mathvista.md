# MathVista (testmini) — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline, plain accuracy over the 1,000 testmini Cases, can sit beside a run of [inspect_evals' `mathvista` at v0.20.0](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/mathvista) (which publishes no reference number of its own), **not** beside the [paper's Table 2](https://arxiv.org/abs/2310.02255v3) (GPT-4V 49.9, human 60.3). Against inspect_evals every dimension matches with evidence: all 1,000 Cases render to the same text, the same picture bytes and the same answer key as inspect_evals' own solver produces (Checks run 7); 13,374 pre-written replies mark identically through our grade hook and inspect_evals' `mathvista_scorer` (Checks run 9); five fixed mark vectors roll up to the same four decimals (Checks run 11). The one deviation from inspect_evals is declared and cosmetic (serving order pinned by `shuffle_seed`, bound 0): `sum of bounds against inspect_evals = 0/1000 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`. inspect_evals itself differs from the authors' harness by design: the harness prompts with the dataset's `Hint: … Question: … Choices: (A) …` query, extracts the short answer with an OpenAI chat model and normalises it (letter → option text, Levenshtein nearest option, `int(float())`, `round(float, precision)`) before an equality check, where inspect_evals demands a literal `ANSWER: <letter>` / `ANSWER: <text>` line equal to the key; on the bare-extraction answer sheets that gap flips 540/540 multiple-choice and 460/460 free-form marks (Upstream notes), so `bound inspect_evals vs original harness = unbounded > 0.005`, which is what makes the verdict `comparable-to-inspect` and not `comparable-to-paper`.

## Upstream notes

- **inspect_evals vs the original harness: answer extraction and metric differ by design, bound `unbounded`.** The harness grades in three stages ([`fork:README.md:344,371`](https://github.com/lupantech/MathVista/tree/827910f3cad39653816236d6ff60dee29b8a2138); paper §3.1): a model reply, a chat-model extraction of the short answer (`fork:evaluation/extract_answer.py:35-77`, few-shot prompt `fork:evaluation/prompts/ext_ans.py`), then normalisation and equality (`fork:evaluation/calculate_score.py:24-72,75-85`): a letter or `(X)` becomes the option's text (`:39-48`), anything else snaps to the Levenshtein-nearest option (`:51`), integers go through `int(float())` (`:56`), floats through `round(float(), precision)` (`:62`), and the result is compared with the dataset's `answer` text. inspect_evals has no extractor and no normalisation: the reply must carry `ANSWER: <letter>` (multiple choice) or an `ANSWER: <text>` last line equal to the key, case ignored (`inspect_evals:mathvista/mathvista.py:86-120`). The bare-extraction sheets (Checks run 10) show the gap on every Case: a bare `B` is right under the harness on 540/540 and wrong under inspect_evals; a bare `991` right on 460/460 vs wrong; `991.` right on 418 vs wrong; `991.00` right on 438 vs 20. Our row's own description names this (`benchmarks.py:6849-6850`). Any Candidate that answers in a form other than inspect's literal line marks lower here than under the paper's protocol; nothing bounds it.
- **inspect_evals vs the original harness: the prompt differs, bound `unbounded`.** The harness and the paper prompt with the dataset's `query`: `Hint: Please answer the question and provide the correct option letter, e.g., A, B, C, D, at the end.\nQuestion: …\nChoices:\n(A) …` (`fork:evaluation/build_query.py:215,243,265`; equal to the Hub `query` on 1000/1000). inspect_evals replaces that for multiple choice with inspect's single-answer template over the bare `question` and `A) …` options (`mathvista.py:127-130,174`), and for free-form wraps the `query` (hint kept) in its own `ANSWER: $ANSWER` instruction (`mathvista.py:58-62,135-137`). Same question, different wording and answer format request.
- **Duplicate option texts: inspect_evals keys one letter where the harness accepts the text.** pids 587, 740, 781 repeat an option text (Checks run 6). For pid 781 (`['9', '12', '18', '18']`, answer `18`, our Case 587) inspect_evals' key is the first matching letter `C` (`get_multi_choice_as_letter`, `mathvista.py:211-219`, `.index(answer)` at `:218`), so `ANSWER: D` is wrong under inspect_evals and ours but right under the harness, which maps the letter back to the text. Bound 1/1000, inside the unbounded gap above; we inherit inspect_evals' key.
- **Paper vs harness: the extractor model.** The paper says GPT-4 extracts the answer (§3.1, Table 8). The harness at `827910f3` calls `get_chat_response(full_prompt, openai.api_key)` (`fork:evaluation/extract_answer.py:76`) whose default is `model="gpt-3.5-turbo", temperature=0, max_tokens=256` (`fork:utilities.py:159`); the harness is the reference. Later commits (2024-02 to 2026-11, HEAD `5f6b4dec`) rewrite the extractor for Azure OpenAI and add `--ignore_empty_extractions` (default off, `9d65741` 2026-11-03); not the pinned reference, not counted.
- **Paper's headline number: a different process by design.** GPT-4V's 49.9 came from the ChatGPT playground by hand, 7–15 Oct 2023 (`fork:README.md:129`; Table 2 "GPT-4V (Playground)"), then the extraction and scoring above. No harness generation step exists for the headline model; the human 60.3 is AMT annotators (`fork:README.md:125`).
- **Dataset: harness and Hub agree, bound 0.** `fork:data/testmini.json` equals the pinned Hub revision on every field compared and `fork:data/query.json` equals the Hub `query` column on all 1000 testmini pids (Checks run 6).
- **inspect_evals' own version.** `eval.yaml` version `2-A` (changelog 2026-02-16), `dataset_samples: 1000`, README: "An accuracy is calculated over the datapoints"; it publishes no baseline number.
