# AGIEval LSAT-LR — Fidelity Record

## Verdict

**`unverified`.** Our Candidate sees exactly what [inspect_evals v0.20.0 `agie_lsat_lr`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/agieval) sends, and we mark it the same way. All 510 Case inputs are byte-identical to the prompt inspect's own `multiple_choice` solver renders. On 17 answer sheets per Case (8,670 marks), our scorer adapter and inspect's own solver plus `choice()` disagree on 0 marks. The roll-up equals inspect's `accuracy()` to four decimals on seven vectors. One deviation stays open: **D1, undeclared**. The inspect_evals Task fixes `GenerateConfig(temperature=0, max_tokens=2048, top_p=1)` (`inspect_evals:agieval/utils.py:196`), and our row applies none of it. That changes what the Candidate writes, not how a reply is marked. It is `possibly-score-changing` with bound `unknown`, so by the rule the verdict is `unverified` (bounds vs inspect_evals = 0/510 marked + D1 `unknown`). Once a paid run bounds D1 at ≤ 0.005, the record becomes `comparable-to-inspect`. It can never be `comparable-to-paper`. inspect_evals and the [AGIEval harness](https://github.com/ruixiangcui/AGIEval/tree/84ab72d94318290aad2e4ec820d535a95a1f7552) are different examiners. The harness uses a "Among A through E, the answer is" completion prompt with a first-capital-letter extractor, where inspect uses an `ANSWER: $LETTER` template and regex. Given the same `ANSWER: X` reply they disagree on 411/510 Cases, and given a bare `X` on 510/510, so that gap is `unbounded` (Upstream notes). The paper numbers our row shows (GPT-4 85.9 few-shot, Table 3; 80.6 zero-shot, Table 2, [Zhong et al. 2023 v2](https://arxiv.org/abs/2304.06364v2)) come from that harness's process.

- **Undeclared (a finding).** The row (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2198-2257`) carries no `# NAMED DEVIATION` or "Named Deviation:" line, and its description does not mention the dropped config. It is not applied here.
- **Where.** Theirs: `inspect_evals:agieval/utils.py:196`. Ours: no setting exists, because the importer never reads `task.config` (`benchmarks.py:4190`).
- **What differs.** An `inspect eval` run asks the model for greedy decoding (temperature 0, top_p 1) and cuts the reply at 2,048 tokens. Our Candidate answers with its provider's defaults and no Benchmark-level cap. A reply longer than 2,048 tokens that puts `ANSWER: X` on its last line scores 1 with us but 0 under inspect, where the truncation drops the answer. Sampling temperature changes which letter a model picks.
- **Severity / bound.** `possibly-score-changing`, `unknown`. Grading is unaffected (D1 changes the reply, not the mark), and no free check can measure it.
- **Evidence.** The source line above. The built Task's config printed by Checks run 5. The row `awk` with no hits (Checks run 3).

  1. Run all 510 Cases with `temperature=0, top_p=1, max_tokens=2048`, the inspect_evals config.
  2. Run them once with no settings, our current behaviour.
  3. Repeat the no-settings arm once to measure run-to-run noise.

  Bound = |headline(inspect config) − headline(default)| beyond that noise. Also count the Cases whose `finish_reason` is `length` under the 2048 cap. If the bound is ≤ 0.005, D1 becomes `score-changing` with that bound and the verdict becomes `comparable-to-inspect`; otherwise `not-comparable` until the row applies the config or declares it. Grading is `choice()`, so no judge tokens are spent; about 1,530 Candidate calls in all.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `agieval`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/agieval) departs from [ruixiangcui/AGIEval@84ab72d9](https://github.com/ruixiangcui/AGIEval/tree/84ab72d94318290aad2e4ec820d535a95a1f7552) in three ways:
  - **Prompt.** inspect sends one user message with no system message: "Answer the following multiple choice question. The last line of your response should be of the following format: 'ANSWER: $LETTER' …", then the passage and question, with `A) option` lines (`inspect_evals:agieval/utils.py:68-76`). The harness sends system "You are a helpful AI assistant." (`fork:openai_api.py:87-89`), then `passage + "Q: " + question + " Answer Choices: (A)… (E)…\nA: Among A through E, the answer is"` (`fork:src/dataset_loader.py:33-35`). In its default zero-shot setting it follows with a second call that appends the first reply and "Therefore, among A through E, the answer is" (`:255`, `fork:run_prediction.py:172-198`).
  - **Answer extraction.** inspect reads the last `ANSWER:` line (`inspect_ai:solver/_multiple_choice.py:99`, `:108`). The harness takes the first capital A–F anywhere in the reply for zero-shot (`fork:src/post_process.py:72-78`, `:187-189`), and `answer is .*?([A-G])` then the first capital for few-shot (`:29-43`, `:64-69`).
  - **Effect on the sheets.** The same `ANSWER: X` reply is right under inspect on 510/510 Cases. The harness reads the `A` of "ANSWER" and is right on only 99/510. A bare `X` is right under the harness on 510/510 and wrong under inspect on 510/510.

  The gap depends on how a Candidate formats its replies, so no free check bounds it: `unbounded`. That is why the best verdict reachable is `comparable-to-inspect`.
- **Harness vs paper.** They agree on temperature 0. The paper says the generation cap is 2048 tokens (§4.2.4). The harness's chat call sets no `max_tokens` (`fork:openai_api.py:98-103`), and 2048 appears only as the few-shot demonstration budget (`fork:run_prediction.py:151`) and as 2000 on the completion API (`fork:openai_api.py:121`). inspect_evals' `max_tokens=2048` follows the paper's text, not the harness. The harness wins; this is recorded, not counted. The paper's §4.2.2 zero-shot-CoT two-step prompt ("Let's think step by step", then "Explanation is: … The answer is:") differs in wording from the harness's two-stage zero-shot suffixes. The harness wins.
- **The harness at HEAD is the v1.1 rerun.** HEAD `84ab72d9` (2024-06-13) targets GPT-3.5-Turbo and GPT-4o on data v1.1 (`fork:README.md:36-46`). The paper's 2023 GPT-4 numbers came from an earlier revision of the scripts. `lsat-lr.jsonl` is byte-identical in `data/v1` and `data/v1_1`, so the rows are the same.
- **Our row's frontier score is from a different setting.** `FrontierScore(score=0.859, model='GPT-4')` (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2249-2250`) is the paper's few-shot (5-shot, no CoT) Table 3 number. This Benchmark serves inspect's zero-shot prompt, and the paper's zero-shot GPT-4 figure is 80.6 (Table 2). The row's comment says so. It is a provenance note, not a marking difference.
- **No published inspect_evals number.** The eval's README has no evaluation-report section. "comparable-to-inspect" would mean comparable to a run of the pinned eval, not to a number inspect_evals printed.
