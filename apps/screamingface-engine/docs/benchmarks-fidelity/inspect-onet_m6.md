# O-NET M6 — Fidelity Record

## Verdict

**`not-comparable`.** Our headline is plain accuracy over 372 [O-NET M6](https://huggingface.co/datasets/matichon/thai-onet-m6-exam/tree/93ffb5e3f3ec630b73e501937805984dd24f2365) questions, which come from Thailand's grade-12 national exam for 2019 to 2021. It is built to sit beside a run of [inspect_evals v0.20.0 `onet_m6`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/onet), which uses `system_message` + `multiple_choice(cot=True)`, the `choice()` scorer and `accuracy`. It does not sit beside it, because the row leaves out questions inspect marks.

The row declares 25 left-out questions (D1-D3), and they fall into three groups:
- **D1, 6 questions inspect cannot mark (bound 0).** inspect_evals v0.20.0's own `choice()` scorer raises `ValueError` on them, because the answer letter points past the last choice. inspect's default `eval()` therefore stops with `status error`. With `fail_on_error=False` it scores 391, which is exactly the 397 less these 6.
- **D2, 18 questions inspect marks against a wrongly split option list.** The parse error is inspect_evals' own, and the fix is its open PR #2590.
- **D3, 1 question whose source gives the key's text to two letters.**

D2 and D3 are questions inspect does mark, so leaving them out moves the headline. The arithmetic: `bounds against inspect_evals = D1 0/391 + D2 18/391 + D3 1/391 = 19/391 = 0.0486 > COMPARABLE_TOLERANCE (0.005)`. Counted against inspect's catalogue count instead, it is `25/397 = 0.0630`. By rule (spec §2.3), bounds summing above tolerance give `not-comparable`. That holds whatever D4 turns out to be.

D4 is the eval's system message, which arrives as leading user text instead of a system turn. It is undeclared on the row and `possibly-score-changing`, bound `unknown`, so even with no exclusions the record would read `unverified` until a paid run bounds it.

Everything a model-free check can reach matches inspect_evals on the 372 we serve:
- **Text:** every Case's text equals inspect's system text + blank line + user prompt, through inspect's own solver chain and its real `eval()`.
- **Marks:** all 7,440 answer-sheet marks agree.
- **Roll-up:** the headline equals inspect's `accuracy()` to four decimals on 7 vectors.

**Not comparable to the paper either.** The [OpenThaiGPT 1.5 paper](https://arxiv.org/abs/2411.07238v2) (Table 3) and the authors' [openthaigpt_eval harness](https://github.com/OpenThaiGPT/openthaigpt_eval/tree/715e8730a9e4f233b3e80ba38ce5ee7dc319b363) score O-NET M6 differently:
- they score per subject, on 217 questions from 2021 only (Thai 65, Math 17, Social 55, Science 28, English 52);
- they ask for `'คำตอบที่ถูกต้องคือ (n)'`;
- they take the first `\([1-5]\)` in the reply;
- they publish no pooled O-NET M6 number.

On the answer sheets, the harness and inspect disagree on all 193 shared Cases for each reply format (Upstream notes, `unbounded`). The row's Frontier Score is `NotPublished`, so no published number is claimed.

## Deviations

### D1 — six questions inspect_evals cannot mark are left out

- **Declared.** `# NAMED DEVIATION (owner decision 2026-09-29, OME-1269)` at `apps/screamingface-engine/src/screamingface_engine_inspect/prepare.py:1074-1078`, ids at `:1080-1085` (`2019_10ข_6985`, `2020_28_177b`, `2020_43_b673`, `2021_10_0325`, `2021_13_1922`, `2021_4_b447`). The row's description says it too (`benchmarks.py:1872`, "points past the last choice (6)").
- **What differs.** inspect_evals builds these 6 with an answer letter past the last parsed choice. On every reply, its own `choice()` raises `ValueError("Choice scorer target references answer(s) beyond the task's N choices: X")` (`inspect_ai:scorer/_choice.py:32-41`). The audit got this on all 6: `2021_10_0325` (1 choice, key E), `2021_13_1922` (3, D), `2020_28_177b` (4, E), `2019_10ข_6985` (3, D), `2020_43_b673` (4, E) and `2021_4_b447` (4, E) (Checks run 4). In inspect's real `eval()` with default settings, the run stops: `status error`, `ValueError(... 1 choices: E)`, `samples logged 24`. With `fail_on_error=False` it completes with `errored 6`, `scored samples 391` and accuracy over those 391 (Checks run 5).
- **Severity / bound.** `cosmetic`, `0`. inspect gives these Cases no mark in any run that completes, so leaving them out gives the same denominator and the same marks as inspect's only completing configuration.

### D2 — eighteen questions inspect_evals parses wrongly are left out

- **Declared.** `# NAMED DEVIATION (OME-1701 PR 6, 2026-10-21)` at `prepare.py:1086-1097`. Ids: the 16 whose key names another option's text (`:1098-1114`) and the 2 with an option missing (`:1115-1117`). The description states it at `benchmarks.py:1869-1873`.
- **Where.** Theirs: `split_numbered_list` splits only at `\d+\.\s` (`inspect_evals:onet/onet.py:120`). The key comes from the record's own number (`:128-146`, `:162-166`). So "1.x" or "1 x" options are lost or merged, and a year inside an option is split off (`2021_31_213c` becomes 22 choices, Checks run 4). inspect_evals PR #2590 (open) parses in number order. `test_the_excluded_ids_are_exactly_where_the_two_parses_differ` (`tests/unit/inspect/test_onet_m6_option_parse_exclusions.py:195`) pins that these are exactly the Samples where the two parses differ. It passed (Checks run 7).
- **What differs.** inspect marks all 18. On the gold-letter sheet it gives 1.0 to each (Checks run 4), but against a wrong option list. For example, `2021_40_e2b5`'s key text is "careless" where the record's answer is "restless", pinned by `test_tripwire_inspect_evals_still_keys_2021_40_e2b5_to_careless` (`:254`). A Candidate that answers the real question can be marked differently from one that answers the garbled list, so inspect's headline over these 18 is not ours.
- **Severity / bound.** `score-changing`, `18/391 = 0.0460`, the 18 ids above.

### D3 — one question whose source gives the key's text to two letters is left out

- **Declared.** `# A SEPARATE NAMED DEVIATION (OME-1701 PR 6 review, 2026-10-21)` at `prepare.py:1118-1121`, id `2020_32_08b1` at `:1122`. The test is `test_2020_32_08b1_is_the_one_agreed_question_whose_key_text_sits_under_two_letters` (`tests/unit/inspect/test_onet_m6_option_parse_exclusions.py:215`), which passed.
- **What differs.** Options C and E have the same text and the key is C, so inspect marks a reply of E wrong. inspect marks this Case; we serve none.
- **Severity / bound.** `score-changing`, `1/391 = 0.0026`.

### D4 — the eval's system message rides inside the user prompt

- **Undeclared on the row; declared at the plugin level** (a finding for the row). The fold is declared plugin-wide at `apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:76` ("Named deviation (contracteval pattern): a Benchmark cannot address a Candidate's system role"). The glossary names "a system message delivered as input text" (`CONTEXT.md:325`). The row has no `# NAMED DEVIATION` line for it (`benchmarks.py:1860-1926`; the three at `prepare.py:1074`, `:1086` and `:1118` are about the exclusions only). The description says "Each prompt opens with the eval's language note" (`benchmarks.py:1876-1877`), which tells a reader the text is there but not that it arrives as user text instead of a system turn. The Task-replay spec's system-text decision names only musr and xstest (`docs/spec/2026-10-02-ome-1460-one-fetch-path.md:259`).
- **Where.** Ours: `SYSTEM_MESSAGE + "\n\n" + user prompt` as one user text (`capture.py:79`, `:538`). The grader receives the same single user message (`scorer_adapter.py:635`). Theirs: `system_message(SYSTEM_MESSAGE)` (`inspect_evals:onet/onet.py:26`, `:62`) inserts a `ChatMessageSystem` (`inspect_ai:solver/_prompt.py:46-70`).
- **What differs.** The text is equal on all 372 Cases, byte for byte (Checks run 4, 5). The Candidate gets "The question can be in either English or Thai." as the opening of the user turn. The scorer never reads it.
- **Severity / bound.** `possibly-score-changing`, `unknown`. Only a paired Candidate run can bound it (Recommended paid runs). It does not affect the verdict, since D2 + D3 already exceed tolerance.

## Recommended paid runs

- **D4, system turn vs folded text.** Use one Candidate on the 372 Cases, with no judge (the scorer is deterministic).
  - **Arm A:** inspect's own `eval()` of `onet_m6()` restricted to the 372 ids, with the system message as a system turn.
  - **Arm B:** the same model sent our prepared Case input as one user turn.
  - **Grading:** score both with `choice()` and compare per-Case marks.
  - **Noise control:** use temperature 0 or at least 3 epochs per arm, so sampling noise is not counted as D4.
  - **Cost:** 744 Candidate calls (×epochs). Replies are long, because the template asks the model to "Think step by step".
  - **What it can change:** this run cannot change the verdict. D2 + D3 already exceed tolerance; it would only close D4.

## Upstream notes

- **inspect_evals vs the original harness: a different exam and a different examiner, `unbounded`.** [inspect_evals v0.20.0 `onet`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/onet) departs from [OpenThaiGPT/openthaigpt_eval@715e8730](https://github.com/OpenThaiGPT/openthaigpt_eval/tree/715e8730a9e4f233b3e80ba38ce5ee7dc319b363) on four dimensions:
  1. **Case set.** The harness's O-NET M6 is 2021 only: 217 questions after the same three-flag filter (`fork:evaluate.py:104`; Thai 65, Math 17, Social 55, Science 28, English 52), from its own CSVs. inspect reads the [matichon Hub copy](https://huggingface.co/datasets/matichon/thai-onet-m6-exam/tree/93ffb5e3f3ec630b73e501937805984dd24f2365), whose filter keeps 397 questions over 2019 to 2021 (217 of them from 2021). Of the harness's 217, 208 matched a Hub row by text with the same key, and 9 did not match (Checks run 6).
  2. **Prompt.** The harness sends `ตอบคำถามดังต่อไปนี้โดยการเลือกคำตอบตาม Choice ที่กำหนดให้เท่านั้น ไม่ต้องอธิบายเพิ่ม อาทิเช่น 'คำตอบที่ถูกต้องคือ (1)'\nคำถาม: {instruction}\nChoice: {input}` as one user message with no system turn (`fork:evaluate.py:111`). The options keep their `(1)…(5)` numbering, and the CSV's literal `\n` sequences are sent as-is. inspect sends an English system line, then the English COT template with letter options.
  3. **Answer extraction.** The harness cuts after a Thai answer prefix and then takes the *first* `\([1-5]\)` (`fork:evaluate.py:40-47`, `:55`). inspect takes the *last* `ANSWER: <letter>` line. On the 193 shared Cases, the two disagree on every Case for both a bare `ANSWER: X` reply and a bare harness-format reply (Checks run 6).
  4. **Roll-up.** The harness reports per exam file and per year, never pooled over subjects (`fork:evaluate.py:164`, `:167`). inspect pools all subjects into one accuracy.

  How often a Candidate's replies fall into each format decides the gap, so it cannot be bounded without a run: `unbounded`. The Case-set difference alone is `180/397` Cases that the harness never asks (the 2019 and 2020 questions).
- **The inspect_evals README quotes numbers its eval does not produce.** The table at `inspect_evals:onet/README.md:54-60` (e.g. OpenThaiGPT 1.5 72B English 90.38) is the paper's Table 3: per subject, on the 2021-only harness set, with the harness's prompt. A pooled inspect run over 397 (or 391) questions is a different number by construction. The row correctly declares `frontier_score=NotPublished` (`benchmarks.py:1918-1923`).
- **The 6 questions inspect cannot mark.** inspect_evals v0.20.0's default `eval()` of `onet_m6` fails with `status error` on the first of the 6 D1 Samples it reaches. That happens because inspect_ai v0.3.263's `choice()` raises on an out-of-range key (`inspect_ai:scorer/_choice.py:29-41`), and the eval leaves `fail_on_error` at its default. Since the eval shuffles unseeded, how many Samples get logged before it stops depends on the run (24 in this audit, Checks run 5). This is an inspect_evals bug, recorded here and not ours.
- **Harness vs paper: the released harness predates the paper's models.** The harness's last commit (2024-04-07) lists the 2024 models only (`fork:README.md:6-23`; `fork:evaluate.py:171-189`). The paper (Nov 2024, v2 Feb 2025) reports OpenThaiGPT 1.5 and Qwen2.5, neither of which this commit can load. The per-subject denominators match the harness's CSVs exactly (65/17/55/28/52), but the paper does not say whether its runs used this prompt and extractor unchanged. The paper's §3.1 also describes the Thai Exam Benchmark's O-NET as "exams from 2021-2025", while its tables and the harness use 2021 only.
- **The Hub copy changed hands.** inspect_evals 3-A repointed the dataset from `openthaigpt/thai-onet-m6-exam` (now HTTP 401) to `matichon/thai-onet-m6-exam` and bumped its comparability version because "byte-level equivalence with the original cannot be verified" (`inspect_evals:onet/README.md:79`). The Hub copy writes options as `1. …` and keys as `5. ข้อ (๕)`, where the harness CSVs write `(1) …` and `(3) …`. That is why the authors' `check_answer` asserts on every Hub row (Checks run 4).
