# CyberMetric-2000 — Fidelity Record

## Verdict

**`unverified`.** Our headline is plain accuracy over the 2,000 CyberMetric-2000 questions. It is built to sit beside a run of [inspect_evals v0.20.0 `cybermetric_2000`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric), which uses a system message, the default `multiple_choice()` template, the `choice()` scorer and the `accuracy` metric. inspect_evals publishes no number for this eval. Our headline is **not** comparable to the paper's Table III (GPT-4o 91.25% on 2k Q; [Tihanyi et al. 2024, v2](https://arxiv.org/abs/2402.07688v2)), which is also the row's Frontier Score. The reason is that inspect_evals marks a different exam from the authors' harness ([cybermetric/CyberMetric@7c565c65](https://github.com/cybermetric/CyberMetric/tree/7c565c65c03ac5bb06b1f94da410cd3f9b91dafe)). First, it pins the December 2024 data file, while the paper's June 2024 numbers came from the February 2024 file, and 114 of the 2,000 Cases differ between the two (`114/2000 = 0.057`). Second, it asks with a different prompt. Third, it extracts the answer differently: the harness takes the first case-insensitive `ANSWER:?\s*[A-D]` anywhere in the reply and re-asks up to five times when that fails. Together these are `unbounded` (Upstream notes). Against inspect_evals, three things hold. (1) Every Case is served with inspect's exact text, key and options. (2) Our 34,000 sheet marks equal inspect's own solver and scorer on every sheet. (3) The roll-up equals inspect's to four decimals on nine vectors. One deviation remains, and it is undeclared: D1, the system message delivered as leading user text. It is `possibly-score-changing` with bound `unknown`. Arithmetic: `bounds against inspect_evals = 0/2000 (dataset, extraction, metric, roll-up) + unknown (D1)`. One `possibly-score-changing` deviation is open, so the rule gives `unverified`. Once D1 is bounded at ≤ 0.005 (at most 10 of 2,000 Cases), the rule gives `comparable-to-inspect`, because inspect_evals vs the original harness is `unbounded` (with a lower bound of 114/2000 = 0.057 from the data alone).

## Deviations

### D1 — the eval's system message rides inside the user prompt

- **Undeclared on the row.** The row carries no `# NAMED DEVIATION` line (`grep -n "NAMED DEVIATION"` over `apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py` gave no line in `2983-3042`, and `prepare.py:402-414` has none, Checks run 7). It has no `named_deviations/` scorer, no `dropped_scorers` and no `excluded_sample_ids` (`None`, Checks run 2), and no linked README. The Task-replay spec's D3 names only musr and xstest (`docs/spec/2026-10-02-ome-1460-one-fetch-path.md:259-262`, `:283`; `grep -n cybermetric` there → no line). Two things come close. The row's description says the questions are "asked with the eval's own system message" (`benchmarks.py:2989`), but does not say the message arrives as user text. The plugin-wide comment at `capture.py:75-78` calls the fold a "Named deviation (contracteval pattern)", and the glossary lists "a system message delivered as input text" as an example (`CONTEXT.md:323-326`). Neither is one of the declaration forms the rule accepts, so this is a finding. Either form would make it declared; it would still be counted the same way.
- **Where.** Ours: `SYSTEM_MESSAGE + "\n\n" + user prompt` as one user text (`apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:79`, `:530-538`). The grader gets that single user message (`scorer_adapter.py:635`). Theirs: `system_message(SYSTEM_MESSAGE)` inserts a `ChatMessageSystem` before the user turn (`inspect_evals:cybermetric/cybermetric.py:35`, `:77`; `inspect_ai:solver/_prompt.py:46-70`). The original harness also sends `{"role": "system"}` then user (`fork:CyberMetric_evaluator.py:31-34`).
- **What differs.** Every byte of text is equal on all 2,000 Cases (Checks run 4). The Candidate receives "You are a security expert who answers questions." as the opening of the user turn, not as a system turn. The scorer never reads it, since `choice()` reads only the reply and the choices.
- **Severity / bound.** `possibly-score-changing`, `unknown`. A Candidate may follow a system instruction differently from user text. This needs a paired Candidate run over the 2,000 Cases (Recommended paid runs). At 2,000 Cases the tolerance is 10 differing marks net (`10/2000 = 0.005`).

## Recommended paid runs

- **D1, system turn vs folded text (bounds the open deviation).** Use one Candidate on all 2,000 Cases with no judge, since the scorer is deterministic.
  - **Arm A:** inspect's own `eval()` of `cybermetric_2000()` (system message as a system turn).
  - **Arm B:** our served Case input as one user message.
  - **Noise floor:** run each arm twice, or fix `temperature=0` where the Candidate allows it. The paper reports 3–4 pp run-to-run variation at temperature 1.0, so the floor matters here.
  - **Readout:** compare per-Case marks and the headline difference. If |A − B| ≤ 0.005 (10 Cases net) beyond the noise floor, D1's bound is that difference and the rule gives `comparable-to-inspect`.
  - **Cost:** Candidate tokens only, about 150 input tokens and a few output tokens per Case per sitting, so roughly 4 × 2,000 short calls. Running the 500 sibling's run first is cheaper and answers the same question for the family's shared prompt shape.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `cybermetric`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric) keeps the harness's system message and its `Question: …\nOptions: A) …, B) …` rendering (`cybermetric.py:35`, `:115-116`; `fork:CyberMetric_evaluator.py:25-26`, `:32`). It changes the rest of the exam [cybermetric/CyberMetric@7c565c65](https://github.com/cybermetric/CyberMetric/tree/7c565c65c03ac5bb06b1f94da410cd3f9b91dafe) gave.
  1. **Data, 114/2000 = 0.057.** inspect_evals pins `205262cd` (2024-12-18, `cybermetric.py:31-32`), which comes after the 2,000-set edit `ec88fb3` ("Updated /fixed questions", 2024-12-17). The paper's v2 (3 Jun 2024) numbers came from the February 2024 file (`0723521`, unchanged until December). Matching by exact question text: 46 pin questions are new, 56 have changed options and 12 have a changed key. That makes 114 Cases where the pin's exam differs from the paper's. The pin also reorders the rows and rebalances the keys to 500 per letter, where the paper-time file had A 487 / B 520 / C 497 / D 496.
  2. **Prompt.** The harness's user turn ends `Choose the correct answer (A, B, C, or D) only. Always return in this format: 'ANSWER: X' ` (`fork:CyberMetric_evaluator.py:26`). inspect wraps the same question in its `SINGLE_ANSWER_TEMPLATE` (`inspect_ai:solver/_multiple_choice.py:17-23`). Because `record_to_sample` sets `choices` to the option *letters* (`cybermetric.py:119`), inspect then appends a second option list that reads `A) A`, `B) B`, `C) C`, `D) D` (`inspect_ai:solver/_multiple_choice.py:57`, `:71`). The real option texts appear only in the comma-joined `Options:` line. See Case 1 in Checks run 4.
  3. **Answer extraction.** The harness takes the **first** case-insensitive `ANSWER:?\s*([A-D])` anywhere in the reply (`fork:CyberMetric_evaluator.py:19`). The colon is optional, and the regex reads the first letter of the following word, so "answer depends" gives D. inspect takes the **last** `ANSWER\s*:` match, requires the colon and an allowed letter (`inspect_ai:solver/_multiple_choice.py:99`, `:108`, `:115`, `:121-123`). On the sheets they disagree on 2000/2000 Cases for four reply shapes and on 1500/2000 for a fifth (Checks run 4).
  4. **Retries.** The harness re-asks the model up to five times when the reply has no parseable letter (`fork:CyberMetric_evaluator.py:24`, `:27-45`), so a format slip costs nothing unless it repeats. inspect asks once and marks an unparseable reply wrong.

  The gap from items 2–4 depends on how a Candidate writes its reply, so it cannot be bounded without a run. Item 1 alone exceeds tolerance. Hence the verdict is at best `comparable-to-inspect`, never `comparable-to-paper`.
- **Harness vs paper: sampling settings.** The paper states "temperature of 1.0, top_p at 0.9, and top_k at 50" for its AWS-hosted models (§IV-A). The published evaluator hard-codes `model="gpt-3.5-turbo-0125"` with no sampling arguments, so it uses the API defaults (`fork:CyberMetric_evaluator.py:29-35`). The harness wins, and the difference is recorded, not counted.
- **The 2,000 set is not human-validated.** The paper says only the 80 and 500 sets are "fully validated by human experts". The 12 key changes and 56 option rewrites in December 2024 (item 1) are the authors' later fixes; neither our row nor inspect_evals claims more for this set.
- **The data file moved again after inspect's pin.** `97faa42` (2026-05-27) changed 1 of the 2,000 rows relative to `205262cd` (position 1638, options changed, key unchanged). Neither inspect_evals v0.20.0 nor we read it. Bound 0 for this record. A future inspect_evals pin bump would change that Case.
- **The row's Frontier Score comes from the paper.** GPT-4o 0.9125 (`benchmarks.py:3034-3039`) was produced by a different exam: the paper-time data, the harness prompt and extraction, and retries. A headline from this Benchmark should not be read against it as like-for-like.
- **Sample ids.** `record_to_sample` sets `id=create_stable_id(...)` (`cybermetric.py:121`), but `load_json_dataset(…, auto_id=True)` (`:109`) numbers the Samples 1..2000 instead (`first sample ids [1, 2, 3, 4, 5]`, Checks run 4). This is cosmetic and changes no mark.
