# SQuAD 2.0 — Fidelity Record

## Verdict

**`unverified`.** Our headline is mean F1 over the 11,873 SQuAD 2.0 dev questions, with exact match beside it as a Named Score. Against [inspect_evals v0.20.0 `squad`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/squad) the grading is identical:
- every Case's text is byte-equal to what inspect sends (system text + blank line + user text) and its target equals inspect's `Sample.target`, on all 11,873 Cases;
- our marks equal inspect's own `f1()` and `exact()` on every one of 379,936 sheet marks (16 sheets x 11,873 Cases x 2 scorers);
- the headline and the `f1` / `exact` columns equal inspect's `mean()` to four decimals on 5 fixed vectors and 16 sheet vectors.

One thing differs that no free check can bound. D1: inspect sends its instruction as a system turn; we send the same bytes as the opening of the user turn. It is declared on the row, and it is `possibly-score-changing` with bound `unknown` until a paired Candidate run measures it. D2 (inspect's clustered `stderr` not published) is cosmetic.

`sum of enumerable bounds against inspect_evals = 0/11873 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`, plus D1 `unknown` (open) → `unverified`.

The paper's numbers (Table 3 of [Rajpurkar et al. 2018](https://arxiv.org/abs/1806.03822v1): human 86.3 EM / 89.0 F1 on dev, 86.9 / 89.5 on test) were marked by the authors' [`evaluate-v2.0.py`](https://github.com/rajpurkar/SQuAD-explorer/blob/eee5fdbf62f8613a7812b03419e6b29617b74fd1/evaluate-v2.0.py), where abstaining means the empty string. inspect_evals' examiner differs from that script on 7 of 16 answer sheets even after mapping "unanswerable" to the empty answer. That gap is `unbounded` (Upstream notes). So once D1 is bounded, the most this record can reach is `comparable-to-inspect`, not `comparable-to-paper`.

## Deviations

### D1 — the eval's system message rides inside the user prompt

- **Declared?** Yes, on the Benchmark. The row's description, served as the Benchmark's description, says: "Named deviation: the eval sends its instruction as a system message; the Benchmark delivers it as leading input text." (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:4031-4033`). The plugin rule is named at `apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:75-77`. The glossary's Named Deviation lists "a system message delivered as input text" and says "It is written on the Benchmark" (`CONTEXT.md:323-326`). The row carries no `# NAMED DEVIATION` comment line. Either way it is counted in the verdict and is not a finding.
- **Where.** Ours: system text + `"\n\n"` + user text, sent as one user turn (`capture.py:79`, `:538`). Theirs: `system_message(SYSTEM_MESSAGE)` inserts a system turn ahead of the user turn (`inspect_evals:squad/squad.py:27-30`, `:49`; `inspect_ai:solver/_prompt.py:46`, `:69-70`).
- **What differs.** Every byte of text is equal on all 11,873 Cases (Checks 4). The Candidate receives the instruction as the opening of its user turn instead of as a system turn: "Using only the context provided in the question itself, you are tasked with answering a question in as few words as possible. If the question is unanswerable, answer with 'unanswerable' in all lowercase." The scorers never read the prompt.
- **Severity / bound.** `possibly-score-changing`, `unknown`. This instruction carries the answer-format convention the scorer depends on: a terse span, and the literal word `unanswerable` for the 5,945 negatives. A Candidate that follows a system turn more strictly than leading user text can change its F1 directly. On the sheets, the wordier `The question is unanswerable.` loses about half the credit on every negative (0.5007 → 0.2514 headline). Only a paired Candidate run can bound this (Recommended paid runs).

### D2 — inspect's clustered standard error is not published

- **Declared?** Stated in a row comment, not as a Named Deviation: "the clustered standard error is a confidence figure, not a score, and is not reproduced" (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:4084-4086`). Counted as an undeclared, cosmetic finding.
- **Where.** Ours: `_accuracy` publishes the mean, `correct`, `scored_cases` and the two Named Score columns (`single_shot.py:1275-1303`). Theirs: `stderr(cluster="context_hash")` (`inspect_evals:squad/squad.py:51`), clustered on the MD5 of the passage (`:62`).
- **What differs.** Only the run's reported uncertainty. The headline and both columns are identical (Checks 6).
- **Severity / bound.** `cosmetic`, `0`.

## Upstream notes

- **inspect_evals vs the authors' `evaluate-v2.0.py`: a different examiner, `unbounded`.** The paper's numbers were marked by the official script (footnote 3; `fork:evaluate-v2.0.py:63-100`). In it, abstaining means predicting the empty string. A negative scores 1 only for an empty prediction, and any non-empty answer scores 0 on both EM and F1. F1 counts tokens as a multiset, and a gold answer that normalises to empty is dropped. inspect_evals instead keys negatives as the word `unanswerable` (`inspect_evals:squad/squad.py:60`, `README.md:112`). It scores with inspect_ai's general `f1`/`exact`, which differ from the script in five ways:
  - they score token **sets** (`_classification.py:93-96`);
  - they split on hyphens as well as spaces (`:144-145`);
  - they `casefold` instead of `lower` (`:172`);
  - they round per-Case F1 to 2 decimals (`:70`);
  - they keep a gold answer that normalises to empty (`.`), so an empty reply matches it (`:67`, `:78-80`).

  The same 16 sheets, official vs inspect (headline F1), with `unanswerable` mapped to `""` for the official script:

  | sheet | official F1 | inspect F1 | Cases differing |
  |---|---|---|---|
  | `The answer is G.` | 0.3321 | 0.5845 | 6,369 |
  | `Answer: G` | 0.3946 | 0.7320 | 6,305 |
  | `G according to the passage` | 0.2893 | 0.4922 | 6,534 |
  | `G G` | 0.3329 | 1.0000 | 11,873 |
  | hyphenated G | 0.6680 | 1.0000 | 3,942 |
  | `The question is unanswerable.` | 0.0010 | 0.2514 | 5,958 |
  | empty | 0.5007 | 0.0003 | 5,948 |

  Without the mapping, every sheet that answers `unanswerable` scores 0 on all 5,945 negatives under the official script. The gold sheets agree once mapped, except three Cases: 11487 (gold `.`) on gold-last, and 9077 and 9081 (`Fußach` upper-cased to `FUSSACH`, equal under `casefold`, not under `lower`). The biggest systematic effect is partial F1 credit on negatives. inspect gives a wordy abstention such as `The question is unanswerable.` F1 0.5 on each negative, where the paper's rule gives 0. The gap depends on how a Candidate words its replies, so it is `unbounded`. It is recorded here and not counted against ours.
- **inspect_evals' README calls the metric "simple accuracy".** `inspect_evals:squad/README.md:103` says so, but the Task reports `mean()` of F1 and of exact (`squad.py:50-51`). Ours reports the same two means. This is a wording issue with no mark effect.
- **inspect's three `.`-gold Cases.** Cases 2752, 10567 and 11487 carry a lone `.` among their accepted answers in the published dev file. `max_exact_score`/`max_f1_score` keep it because `".".strip()` is non-empty, and `_normalize(".")` is `""`, so an empty reply is marked correct on those Cases (bound 3/11873 = 0.00025 on an all-empty run). The official script drops such gold answers (`fork:evaluate-v2.0.py:88-89`). Ours marks them the same way as inspect, so this is not a deviation of ours. It is a reproducible [inspect_ai](https://github.com/UKGovernmentBEIS/inspect_ai) behaviour worth reporting there.
- **Dataset: identical at the source.** The pinned `rajpurkar/squad_v2` validation split is the authors' `dev-v2.0.json` question for question: same 11,873 ids in the same order, same accepted answers, same context and question text (Checks 4). The paper's dev figures (Table 2) match the 5,945 / 5,928 split.
