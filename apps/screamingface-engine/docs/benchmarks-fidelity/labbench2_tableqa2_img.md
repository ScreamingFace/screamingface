## Deviations

### D1 — The judge gets no response schema, so its verdict is read from free text

- **Declared:** yes. The row carries `NAMED DEVIATION: their JSON response schema is not sent; the verdict is read from the reply's result line, the inspect port's own fallback` (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:7587-7589`), and the README says the same under "No response schema" (`apps/screamingface-engine/src/screamingface_engine_inspect/local_tasks/lab_bench_2/README.md:63-67`).
- **Where:** ours is `apps/screamingface-engine/src/screamingface_engine_inspect/local_tasks/lab_bench_2/lab_bench_2.py:270-272` (`judge_until_parsed`, at most 2 redraws) plus `vendor/lab_bench_port.py:30-45`. Theirs is `fork:evals/evaluators.py:45-49,64-67` (pydantic-ai `Agent(output_type=EvaluationResult)`, which forces a `final_result` tool call with a `Literal["correct","incorrect","unsure"]` field, `fork:evals/models.py:8-12`).
- **What differs:** the judge model, its temperature, its token cap and its prompt bytes are all the same. Only the reply format differs: a typed tool call on their side, free text with a `result:` line on ours. Without the tool, the same judge may reason differently in free text. Our reader returns no verdict on prose with no `result` keyword (`"The submitted answer is correct."` → `None`, Checks run 14), and redraws twice before failing the Case. Their schema never yields an unreadable verdict, and on a judge exception they score 0.0 (`fork:evals/evaluators.py:81-83`). On every shape the prompt asks for, our reader gets the right verdict (`rationale:/result:` lines, bold markdown, a JSON object, fenced JSON, capitalised words, the rubric echoed before the verdict; Checks run 14).
- **Severity:** possibly-score-changing. **Bound:** unknown, pending the first run in Recommended paid runs.
- **Evidence:** Checks run 5, 11, 12, 14.

### D2 — The authors' OpenAI and Google runners put the picture before the question

- **Declared:** no, so this is a finding. Neither the row nor the README mentions part order. The README describes the order as "the question … then the picture" (`apps/screamingface-engine/src/screamingface_engine_inspect/local_tasks/lab_bench_2/README.md:37-46`).
- **Where:** ours always sends `[ContentText, ContentImage]` (`apps/screamingface-engine/src/screamingface_engine_inspect/local_tasks/lab_bench_2/lab_bench_2.py:157-158`), and so does the authors' provider-neutral path (`fork:evals/loader.py:119`) and their Anthropic runner (`fork:evals/runners/anthropic.py:113`). Their OpenAI runner appends `input_image` (`fork:evals/runners/openai.py:92`) before `input_text` (`:112`), and their Google runner appends `Part.from_uri` (`fork:evals/runners/google.py:71`) before `Part.from_text` (`:76`).
- **What differs:** the bytes are the same and the order differs. Every no-tools paper report for an OpenAI or Google model came through those runners (`native:openai:gpt-5.2-pro`, `native:openai:gpt-5.2`, `native:google-vertex:gemini-3-pro-preview`; Checks run 6), and that includes the frontier score 0.94 the row cites.
- **Severity:** possibly-score-changing (a vision model may read a table differently depending on whether the question comes first). **Bound:** unknown, pending the second run in Recommended paid runs. For Anthropic Candidates the order matches, so the bound is 0 for them.
- **Evidence:** Checks run 4, 12.
