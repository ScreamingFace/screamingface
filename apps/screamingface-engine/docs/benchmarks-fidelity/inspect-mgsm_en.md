# MGSM (English) — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline is plain accuracy over the 250 English MGSM problems. It can sit beside a run of [inspect_evals v0.20.0 `mgsm`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/mgsm) with `-T languages=en`: zero-shot instruction prompt, `match(numeric=True)` scorer, `accuracy` metric. It is **not** comparable to the paper's English number. [Shi et al. 2022](https://arxiv.org/abs/2210.03057v1), Table 3, reports PaLM-540B 62.4% and GPT-3 53.6% on EN. Those numbers came from a different process by design: 6-shot exemplar prompts that end "The answer is N.", greedy decoding, and an answer-extraction rule the paper never publishes. The authors released data and exemplars only, with no grading code. inspect_evals instead uses [OpenAI simple-evals](https://github.com/openai/simple-evals/tree/652c89d0ca9df547706735883097e9537d40dc47)' zero-shot "Answer:" instruction, and that gap is `unbounded` (Upstream notes).

Against inspect_evals, the comparison is clean:
- Every Case is served with byte-identical prompt and target.
- Our 4,250 marks equal inspect's own `match(numeric=True)` on every one of 17 answer sheets.
- The headline equals inspect's `accuracy()` to four decimals on 5 fixed vectors and 17 sheet vectors.

One cosmetic deviation exists (D1: inspect's clustered `stderr` is not published).

`sum of bounds against inspect_evals = 0/250 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`. inspect_evals vs the original process is `unbounded` → `comparable-to-inspect`.

Note: inspect_evals' default `mgsm` run pools all 11 languages (2,750 Samples, `inspect_evals:mgsm/README.md:58`). That run's number is a different quantity from ours. Ours is comparable to the `languages=en` slice only.

## Upstream notes

- **inspect_evals vs the original process: a different examiner by design, `unbounded`.** The authors' published English numbers (PaLM-540B 62.4%, GPT-3 53.6%, Table 3 of [arXiv 2210.03057v1](https://arxiv.org/abs/2210.03057v1)) come from 6-shot prompts. Those prompts use the exemplars in `fork:mgsm/exemplars.py:17` (`"en"` at `:355`), each solution ending "The answer is N.", with greedy decoding at temperature 0. The paper does not say how the final number was read, and the authors' repository holds no grading code. [inspect_evals v0.20.0 `mgsm`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/mgsm) is different on three counts. It sends a zero-shot instruction asking for `Answer:` on the last line (`inspect_evals:mgsm/mgsm.py:35-37`). It reads the last number anywhere in the reply (`match(numeric=True)`, `:138`). It fixes no decoding parameters (`:137`). The prompt difference (6-shot vs 0-shot) cannot be bounded without paid runs on both prompts. That is why this record says `comparable-to-inspect` rather than `comparable-to-paper`.
- **inspect_evals vs its own named source, simple-evals: same prompt, different extraction.** inspect_evals says its instructions "correspond to those used in the simple-evals" (`inspect_evals:mgsm/README.md:50`). The `en` instruction text is identical (`simple-evals:mgsm_eval.py:33` vs `inspect_evals:mgsm/mgsm.py:35`), and both fetch the same `openaipublic` TSV. The extraction differs. simple-evals takes the last number after the last `Answer` and compares it after stripping commas and trailing zeros (`simple-evals:mgsm_eval.py:83-104`). inspect takes the last whitespace-separated token that parses as a number in the whole reply, normalised to 5 significant digits. The sheets disagree on 6 of 17:
  - a bare `N`: inspect 250, simple-evals 0
  - `The answer is N.`: inspect 250, simple-evals 0
  - `Answer: \boxed{N}`: inspect 0, simple-evals 250
  - `Answer: N%`: inspect 0, simple-evals 250
  - `Answer: -N`: inspect 0, simple-evals 250, since simple-evals' regex drops the sign
  - `Answer: N+1`: inspect 2, simple-evals 0

  The gap depends on how a Candidate formats its replies: `unbounded`, recorded and not counted.
- **inspect's 5-significant-digit rounding can credit a wrong answer, bound 2/250 = 0.008 on the worst sheet.** `normalize_number` formats with `.5g` (`inspect_ai:scorer/_common.py:148-154`), so `114201` and `114200` both become `1.142e+05`, and `276001` and `276000` both become `2.76e+05`. On Cases 202 (`114,200`) and 231 (`276,000`), a reply off by a few tens, within the 5-digit rounding window, is marked correct. On the `N+1` sheet these were the only two Cases credited. Ours and inspect mark them the same way (Checks 5, 6), so this is not a deviation of ours. It is a reproducible [inspect_ai](https://github.com/UKGovernmentBEIS/inspect_ai) behaviour worth reporting there.
- **Dataset: identical at the source.** The `openaipublic` TSV that inspect_evals pins is byte-identical to the authors' `mgsm/mgsm_en.tsv` at `452a21ad` (sha256 `50021d0f…`, Checks 7). The paper's 250 English problems are the problems served here. The row's licence note names the CC-BY-4.0 file in url-nlp (`fork:mgsm/LICENSE`); recorded, no mark effect.
- **The default inspect_evals headline is all 11 languages.** `mgsm()` defaults to `languages="all"` (2,750 Samples, `eval.yaml`), and the README says scores are "averaged over all the eleven languages" (`inspect_evals:mgsm/README.md:58`). Our Benchmark is the documented `languages=en` slice (`apps/screamingface-engine/src/screamingface_engine_inspect/prepare.py:329`, titled "MGSM (English)"). Compare it only to a `-T languages=en` run.
- **No published inspect_evals number.** The eval's README has no evaluation-report section, so "comparable-to-inspect" means comparable to a run of the pinned eval, not to a number inspect_evals printed.
