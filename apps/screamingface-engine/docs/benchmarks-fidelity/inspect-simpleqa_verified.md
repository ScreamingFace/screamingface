# SimpleQA Verified — Fidelity Record

## Verdict

**`not-comparable`.** The Candidate in our row sees what inspect_evals sends. The examiner does the same arithmetic, but it is not the paper's examiner. Our 1,000 Cases match the authors' own Kaggle release v4 row for row, in the same order (question, gold and `original_index`). The Hub pin both sides read is byte-identical to that release (Checks run 3, 6). Inspect's own `eval()` sends the Candidate one user message, and that message equals our Case input on 1,000 of 1,000 Cases (Checks run 6). Our grading hook runs inspect's own `simpleqa_scorer` with the same template, which is byte-identical (6,741 characters) and matches the paper's Appendix A word for word (Checks run 5). It also uses the same `strict` parse, and it builds the same judge prompt on every sheet compared. The run arithmetic matches inspect's `simpleqa_metric` and the paper's formulas to four decimals on 7 vectors (Checks run 8).

The examiner is the gap. The [paper](https://arxiv.org/abs/2509.07968v2) grades with `gpt-4.1-2025-04-14` (§3.2; Table 7 notes). Our row grades with `openrouter/google/gemini-3.1-pro-preview` at `max_tokens 4096`. This is declared at `apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:5561-5569`, and the row's description says the numbers "are not directly comparable to the paper's" (`benchmarks.py:5376-5378`). Spec §2.3 makes a different judge model `not-comparable` by rule. So the row's frontier score of 0.553 (Gemini 2.5 Pro, Table 7 Accuracy, `benchmarks.py:5593-5598`) is the paper's number, not one ours reproduces.

The bound arithmetic, for the record: `bounds vs the paper's process = D2 0 + D4 0 = 0`, with D1 `unknown`. The judge differs by design, so the judge clause of the rule decides the verdict, not the sum. Against inspect_evals, which is the ceiling here (`comparable-to-inspect`), every dimension but the judge matches. D1 is still an open `possibly-score-changing` deviation, so that verdict would be `unverified`. One example shows what D1 does: on the 4,000 answer sheets, 63 of 1,000 Cases got a blank judge reply in one pass. Our headline was 187/937 = 0.1996, while inspect's was 187/1000 = 0.1870 (Checks run 6).

## Deviations

### D1 — a blank judge reply fails the Case and leaves the denominator, where inspect marks it NOT_ATTEMPTED

- **Undeclared on the row.** The rule is plugin-wide (`apps/screamingface-engine/src/screamingface_engine_inspect/judge_provider.py:132-142,308-314`: "A blank completion can never be a grade — refuse loudly"). The SimpleQA Verified row (`benchmarks.py:5362-5601`) carries no `# NAMED DEVIATION` for it, and its description does not mention it. This is a finding for the row.
- **Where.** Ours: `judge_provider.py:308-314` raises, the Case fails, and `coverage_declare` (`benchmarks.py:5385`; `apps/screamingface-engine/src/screamingface_engine/benchmarks/definition.py:39-43`) excludes it from the score (`aggregation.py:94-106`). Theirs: `match = re.search(r"\b([ABC])\b", raw_grade)` → `grade = ... else "C"` → `not_attempted 1.0` (`inspect_evals:simpleqa/scorer.py:120-130`). simple-evals does the same (`fork:simpleqa_eval.py:125-126`).
- **What differs.** In the headline, inspect counts a blank as a 0 in the denominator and we drop it. So ours ≥ inspect's on any run with blanks. Example from Checks run 6, pass 0: 63 blank sheets gave ours 187/937 = 0.1996 against inspect's 187/1000 = 0.1870. Checks run 7: 1 blank in 20 gave 17/19 = 0.8947 against 17/20 = 0.85. The blank is visible in our coverage figure (0.937, 0.95). The headline gap is at most `k/1000`, where `k` is the run's count of blank judge replies.
- **Severity / bound.** `possibly-score-changing`, `unknown`: `k` depends on how often `gemini-3.1-pro-preview` returns an empty completion at `max_tokens 4096`. A reasoning model that spends its budget thinking can return blank content. Any real run's coverage reads off `k` for free. A paired run (Recommended paid runs) bounds it before one.

### D2 — the headline is the share correct; the paper's F1 rides beside it

- **Declared.** `benchmarks.py:5556-5560` ("NAMED DEVIATION, the same one: the headline is the "correct" share; the paper's F1 (f_score) is published beside it"), and the description says it too (`benchmarks.py:5373-5375`). The opt-in list is pinned by `tests/unit/inspect/test_whole_run_metric.py:815-840` (not run here). The row is listed in `tests/unit/inspect/test_failure_policy_rows.py:133-134`, which passed (Checks run 10).
- **Where.** Ours: `whole_run_headline="correct"` over inspect's `simpleqa_metric` (`benchmarks.py:5559-5560`; `single_shot.py:1389-1417`). Paper: F1 is the headline metric (§3), and Table 7 reports Accuracy beside it.
- **Severity / bound.** `cosmetic`, `0`. Every number the paper publishes is published here with the same arithmetic (7 vectors, four decimals, Checks run 8). Only which one is called the headline differs, and the row's frontier score is the paper's Accuracy column (`benchmarks.py:5591-5598`).

### D3 — the judge is Gemini 3.1 Pro Preview, not GPT-4.1

- **Declared.** `benchmarks.py:5562-5565` ("NAMED DEVIATION: the paper graded with gpt-4.1-2025-04-14 … This Benchmark binds inspect's grader role to Gemini 3.1 Pro Preview through our gateway … (owner decision on OME-1602, 2026-10-14)").
- **Where.** Ours: `benchmarks.py:5566-5568`. Paper: §3.2 ("use gpt-4.1-2025-04-14 as an autorater") and the Table 7 notes. Inspect's paper config: `inspect_evals:simpleqa/paper_config/simpleqa_verified.yaml:21-25`.
- **What differs.** Model; temperature (ours unset, so the provider's default; paper config `1.0`); `max_tokens 4096` and `web_search=false` (ours only). The prompt bytes and the parse are the same.
- **Severity / bound.** A different examiner by design: `not-comparable` against the paper by rule. Against an inspect run bound to the same Gemini model it is `possibly-score-changing`, `unknown` (temperature and `max_tokens` only).

### D4 — a Fusion abstain zeroes all three columns, so `attempted` counts it as attempted

- **Undeclared on the row**, though documented in the plugin (`apps/screamingface-engine/src/screamingface_engine_inspect/scorer_metrics.py:157-172`, "A dict value … has every column zeroed").
- **Where.** `scorer_metrics.py:183` (`dict.fromkeys(value, 0.0)`), reached from `single_shot.py:1529-1530`. Inspect has no Candidate abstain. An empty reply is graded by the judge.
- **What differs.** With the vector A, B, C plus one abstained Case: ours gives `correct 0.25`, `f_score 0.3333`, `attempted 0.75`. Inspect, with the judge saying C for the empty reply, gives `0.25`, `0.3333`, `0.50` (Checks run 8). `correct_given_attempted` is the same on both sides.
- **Severity / bound.** `cosmetic`, `0`. The headline and F1 cannot move: an abstained Case is 0 correct and adds to neither correct nor incorrect on either side. Only the `attempted` run metric differs, and only for an abstaining Fusion Candidate.

## Upstream notes

- **The authors' harness is not readable without a Kaggle login.** The paper points to Kaggle for the "evaluation code" (abstract), and inspect_evals' README calls Kaggle "the official implementation" (`inspect_evals:simpleqa/README.md:183`). inspect_evals' paper config makes three claims about the notebook that this audit could not check: it "sets no temperature", it names `JUDGE_MODEL`, and "HuggingFace README confirms gpt-4.1" (`paper_config/simpleqa_verified.yaml:8-11`). The README at the pinned Hub revision names no judge and no model at all (Checks run 3). Only the paper's own text confirms gpt-4.1 (§3.2).
- **Grade parse: inspect's default `strict` vs simple-evals' parse.** The paper says it uses Wei et al.'s grading scheme. simple-evals takes the first capital A, B or C anywhere in the reply (`fork:simpleqa_eval.py:125-126`), which inspect exposes as `grade_parse="paper"` (`inspect_evals:simpleqa/scorer.py:120-121`). Our row uses `strict`, inspect's default (`benchmarks.py:5391`). The two parses disagree when the judge replies with a word instead of a letter: `NOT_ATTEMPTED` and `NOT ATTEMPTED` (strict → not attempted, simple-evals → **correct**), `No Answer`, `ABC` (Checks run 9). The template invites such replies: it ends "Simply reply with either CORRECT, INCORRECT, NOT ATTEMPTED" before the letter instructions (`grader_templates.py:183,201`). What the Kaggle notebook does is unknown. Bound: unknown, the share of judge replies in those shapes. inspect_evals' changelog (README `:236`) says `strict` was chosen to reject exactly these false positives.
- **The dataset moved under the paper, one row at a time.** The Hub pin both sides read equals Kaggle v4 (2025-09-03). v3 (2025-07-24) had `May 1992` as the gold for Case 236 (`original_index 1054`), where v4 has `20 May 1992`. v5 (2026-03-09, a day before paper v2) rewords Case 16 (`original_index 55`) from "latitude" to "longitude" of Lilongwe. The gold `33.7738` is Lilongwe's longitude (its latitude is about −13.97), so the pinned question has a wrong gold. Table 7 is identical in paper v1 and v2, so it predates v5. If the paper's numbers were run on v3, the bound against them is `1/1000 = 0.001`. Against today's Kaggle leaderboard (v5) it is also `1/1000`. inspect_evals and we both serve v4, the wrong-gold row included. Worth a report to inspect_evals (bump the pin to a v5 mirror).
- **A blank judge reply means "not attempted" upstream.** Both inspect's `simpleqa_scorer` (`scorer.py:124`) and simple-evals (`simpleqa_eval.py:126`) default a reply with no letter, blank included, to `C`. Our plugin-wide refusal of a blank judge reply is the stricter reading. Nothing upstream is wrong. D1 records the difference for our row.
