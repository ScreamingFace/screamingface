## Deviations

### D1 — inspect_evals' generation settings (temperature 0, 2,048 max tokens, top_p 1) are not applied, and the row does not say so

- **Undeclared: a finding.** The row (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2377-2436`) has no `# NAMED DEVIATION` line, no `params`, and no sentence in its description (`:2381-2389`) about generation settings. It sets no `dropped_scorers` or `excluded_sample_ids`, and links no README. The drop follows from a catalogue-wide rule: the importer never reads `task.config` (`grep -c 'task.config' importer.py` → `0`). The rule is written in `apps/screamingface-engine/docs/importing-an-inspect-eval.md:106`. That section's own preamble (`:101`) says "the row names the deviation a reader would otherwise have to discover". Other rows follow that convention: MATH has `# Named Deviation: the Task's config=GenerateConfig(temperature=0.5) is not applied` at `benchmarks.py:4189-4191`, following plan decision D10 (`docs/plan/2026-10-05-OME-1268-multi-score-benchmarks.md:70`), and MMMU says it in its description. This row does neither.
- **Where.** Theirs: `inspect_evals:agieval/utils.py:196`. Ours: no setting. Capture accepts and ignores the generation config (`apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:246-247`), and the importer drops `task.config`.
- **What differs.** An inspect_evals run asks for greedy decoding (temperature 0, top_p 1) and cuts each reply at 2,048 tokens. Our Candidate answers with its provider's defaults and no inspect-set token cap. The cap can move marks in either direction. When a reasoning-heavy reply is cut at 2,048 tokens, inspect never sees its final `ANSWER:` line and marks the Case 0, while ours may mark the same reply right. When a reply is sampled at a non-zero temperature, ours can wander where inspect's greedy reply would not. Some reasoning models reject or ignore temperature anyway.
- **Severity / bound.** `possibly-score-changing`, `unknown`. It changes what the Candidate writes, not how a reply is marked (every mark identical, Checks run 5). Only a paid run can measure it.
- **Evidence.** The two source locations above; `task.config temperature 0.0 max_tokens 2048 top_p 1.0` (Checks run 5); the empty `awk` over the row (Checks run 3).

## Recommended paid runs

- **D1 (sampling): 206 Cases × 3 arms, no judge.** Pick one Candidate that accepts `temperature`, `top_p` and `max_tokens`. Run all 206 Cases three times: once with `temperature=0, top_p=1, max_tokens=2048` (inspect_evals' settings), once with no settings (ours), and once more with no settings to measure run-to-run noise. Bound = |headline(inspect settings) − headline(ours)| beyond that noise. If the bound is ≤ 0.005 (about 1 Case in 206), D1 becomes `score-changing` with that bound and, once the row declares it, the verdict becomes `comparable-to-inspect`. Grading is `choice()`, so no judge tokens are spent. Cost: 618 Candidate calls on passages of about 4,700 characters.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `agieval`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/agieval) says it is "based on the original implementation" (`inspect_evals:agieval/README.md:5`), but it departs from [ruixiangcui/AGIEval@84ab72d9](https://github.com/ruixiangcui/AGIEval/tree/84ab72d94318290aad2e4ec820d535a95a1f7552) on three dimensions.
  1. **Prompt.** inspect sends one user message, `Answer the following multiple choice question. The last line of your response should be of the following format: 'ANSWER: $LETTER' …`, then `passage\n\nquestion` and `A) option` lines (`inspect_evals:agieval/utils.py:68-76`, `:85-89`). The harness sends a system message, `You are a helpful AI assistant.` (`fork:openai_api.py:88`), and a two-stage zero-shot exchange. Stage 1 is `passage + "Q: " + question + " Answer Choices: (A)… (B)…\nA: Among A through D, the answer is` (`fork:src/dataset_loader.py:33-35`). Stage 2 is that context, plus the stage-1 reply, plus `Therefore, among A through E, the answer is` (`:255`, `:274`; `fork:run_prediction.py:166`, `:190-195`).
  2. **Answer extraction.** inspect reads the last `ANSWER:` line (`inspect_ai:solver/_multiple_choice.py:98-115`). The harness takes the first capital letter in A–F anywhere in the stage-2 reply (`fork:src/post_process.py:72-78`, `:187-189`).
  3. **Sampling.** Both use temperature 0. inspect_evals adds `max_tokens=2048, top_p=1` from the paper (`utils.py:195-196`).

  On the sheets, the reply `ANSWER: <gold>` is right under inspect on 206/206 Cases but right under the harness only on the 64 Cases keyed A, because the harness reads the `A` of `ANSWER`. The reply `(<gold>)`, the natural reply to the harness's own `the answer is` prompt, is right under the harness on 206/206 and wrong under inspect on 206/206. The gap depends on how a Candidate formats its replies, so it cannot be bounded without a run: `unbounded`, hence not `comparable-to-paper`.

The harness asks twice (above), its chat call sets `temperature=0` and `stop=["<|im_end|>"]` with no `max_tokens` (`fork:openai_api.py:98-103`; the same at `666a489:openai_api.py:89-102`), and only the completion path sets `max_tokens=2000` (`fork:openai_api.py:121`). Its stage-2 suffix says `among A through E` for four-option SAT questions (`fork:src/dataset_loader.py:255`).
