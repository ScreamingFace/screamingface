# PIQA — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline is plain accuracy over the 1,838 PIQA validation questions, and it can sit beside a run of [inspect_evals v0.20.0 `piqa`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/piqa): the eval's own two-option `ANSWER: $LETTER` template through `multiple_choice()`, the `choice()` scorer, the `accuracy` metric, and no generation settings. Against inspect_evals there is nothing to bound. All 1,838 Cases are the same rows in the same order, with the same key and the same two options. Every Case carries the same prompt bytes in one user message, with no system message. Our real served Benchmark and inspect's own solver plus scorer gave the same mark on all 38,598 sheet marks, and the roll-up is equal to four decimals on eight vectors. Nothing is declared, and no undeclared difference was found.

`sum of bounds against inspect_evals = 0/1838 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`

It is **not** comparable to the paper's model numbers ([Bisk et al. 2019, v1](https://arxiv.org/abs/1911.11641v1), Table 1: RoBERTa 79.2 validation / 77.1 test, GPT 70.9 / 69.2, BERT 67.1 / 66.8). Those come from a different process by design. The authors fine-tuned classifiers that score goal+solution pairs through a `[CLS]` head and take a softmax over the two options. There is no prompt and no reply, and the test column is the hidden-label leaderboard split. The data and the rubric agree with ours. The [authors' own `valid.jsonl` / `valid-labels.lst`](https://github.com/ybisk/ybisk.github.io/tree/21edab439af693b961be2f069e8690a88d3b4e37/piqa) match our 1,838 Cases row for row. Our key split (B 928/1838 = 50.5%) reproduces the paper's validation "Majority Class 50.5". "Simple accuracy" is the authors' stated metric. But the examiner being marked is a different kind of thing, so the gap cannot be bounded:

`inspect_evals vs original harness = unbounded > COMPARABLE_TOLERANCE (0.005)` (Upstream notes) → `comparable-to-inspect`
