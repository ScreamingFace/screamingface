## Verdict

**`unverified`.** Our headline is `expression_exact_match` accuracy over the 5,000-problem MATH test split as served by [inspect_evals v0.20.0 `math`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/math), with `expression_exact_match_sympy` beside it as a Named Score. Against inspect_evals the exam is the same: the same 5,000 rows of [`DigitalLearningGmbH/MATH-lighteval@0530c786`](https://huggingface.co/datasets/DigitalLearningGmbH/MATH-lighteval/tree/0530c78699ea5e8eb5530600900e1f328b48acad) with identical targets, byte-identical prompts on 5,000/5,000 Cases, and the same roll-up to four decimals on 25/25 vectors. The marks agree on every answer sheet whose `ANSWER:` line carries no wrapping. **Two declared differences remain open, and their size depends on the run.** D1: our scorers read the `ANSWER:` line through an extraction that unwraps `\boxed{}`, outer `\(..\)` / `\[..\]`, markdown bold and a trailing carriage return or tab ([inspect_evals PR #2199](https://github.com/UKGovernmentBEIS/inspect_evals/pull/2199) and [PR #2340](https://github.com/UKGovernmentBEIS/inspect_evals/pull/2340), both still open, plus two steps of ours). On the sheets it turns misses into credits on up to 4,999 of 5,000 Cases per wrapped form, and never the reverse. D2: the Task's `temperature=0.5` is not applied. Neither has a Case list before a run, so both are `possibly-score-changing` with bound `unknown`: `sum of enumerable bounds against inspect_evals = 0/5000 = 0.0000`, plus D1 `unknown` and D2 `unknown` (open) → `unverified`. A run whose Report shows zero replies with a wrapped `ANSWER:` line settles D1 for that run. D2 needs the paid run below. Against the paper there is no comparison by design. Its Table 2 numbers (GPT-3 175B 8-shot direct answer at temperature 0, 5.2%; GPT-2 1.5B fine-tuned with beam search, 6.9%) come from a different prompt, decoding and extraction process, and inspect_evals vs the authors is `unbounded` (Upstream notes). The row's Frontier Score (OpenAI o1, 0.948) is a vendor-run number. So `comparable-to-paper` is out of reach, and `comparable-to-inspect` holds only for a run where D1 and D2 are shown to move nothing.

The bold and line-ending steps are ours.
- **Where.** Ours: `apps/screamingface-engine/src/screamingface_engine_inspect/named_deviations/math/math.py:182-219` (extraction), `:225-231` (whitespace and bold), `:234-244` (explanation only). Theirs: `inspect_evals:math/utils.py:124-133`.
- **What differs.** A reply whose last `ANSWER:` line carries `\boxed{…}`, an outer `\(…\)` / `\[…\]`, markdown bold around the line or the answer, or a trailing `\r` / `\t` is credited by ours and marked wrong by v0.20.0. With two boxes on the line, the last one is graded. Because `AnswerPattern.LINE` is case-insensitive, the same holds for a prose `answer:` on the last line, as in four of the dataset's own solutions (Cases 1303, 1497, 2700, 3682: inspect copies `$2002-56-6=\boxed{1940}$.`, ours `1940`). On the sheets it never turns a credit into a miss. It acts on both columns.
- **Severity / bound.** `possibly-score-changing`, `unknown`. It moves exactly the Cases whose reply has a wrapped final `ANSWER:` line, which depends on the Candidate. On the sheets it is up to 4,999/5,000 per wrapped form. On a finished run it is countable for free: run both extractors over the stored replies.
- **Evidence.** Checks 6 (sheets), Checks 8 (`test_tripwire_a_wrapped_right_answer_inspect_evals_fails_is_right_under_ours`, `apps/screamingface-engine/tests/unit/inspect/test_named_deviation_math.py:91`, asserts v0.20.0 INCORRECT and ours CORRECT; `test_two_boxes_on_the_answer_line_grade_the_last_one` `:117`).

## Recommended paid runs

- **D2, temperature (needed to settle the verdict).** One Candidate, all 5,000 Cases, twice. Run A as we serve it (the Candidate's own temperature). Run B with `temperature=0.5`, inspect's Task setting. Same `max_tokens` on both. Compare the `expression_exact_match` headlines. If `|A − B| ≤ 0.005` for the Candidates in question, D2 can be bounded below tolerance. Otherwise it stays open per Candidate. No judge is involved. Each run costs about 5,000 Candidate calls. ## Upstream notes

- **inspect_evals vs the authors' process: `unbounded`, by design.** The authors' published numbers come from two processes, neither of which is inspect's. (a) GPT-3 few-shot: an 8-shot prompt of problem/answer pairs with no solutions, ending `"Answer: $"`, temperature 0, up to 20 tokens, with the answer read from the top logprob token up to `$` / `###` / newline (`fork:modeling/evaluate_gpt3.py:11-40`, `:51-58`; paper §4.1). (b) GPT-2 fine-tuned on MATH with beam search, with the answer read from the last `\boxed{}` of the generation (`fork:modeling/eval_math_gpt.py:174-178`, `:204-211`). inspect_evals runs zero-shot chain-of-thought, reads the last `ANSWER:` line, and samples at temperature 0.5 (`inspect_evals:math/math.py:60-66`, `:111`; `utils.py:124-133`). The compare steps are close but not equal. On the plain sheet inspect's `strip_string` and the authors' `_strip_string` agree on 5,000/5,000. inspect also strips bare `$` (`inspect_evals:math/utils.py:311-312`; the authors strip only `\$`, `fork:modeling/math_equivalence.py:97`), so `ANSWER: $t$` is 4,999 credits under inspect's compare and 0 under the authors'. `_remove_right_units` also differs: the authors assert one split (`fork:modeling/math_equivalence.py:46-53`), and inspect partitions (`inspect_evals:math/utils.py:404-406`). inspect also adds a sympy column (Minerva, [Lewkowycz et al. 2022](https://arxiv.org/abs/2206.14858)) and a model-graded column the paper does not have. inspect_evals publishes no results table for `math`, so its side of the comparison is a run of v0.20.0.
- **The row's Frontier Score is a vendor number.** `FrontierScore(score=0.948, model="OpenAI o1", source_url="https://openai.com/index/learning-to-reason-with-llms/")` (`benchmarks.py:4150-4155`) came from OpenAI's own unpublished harness. Its prompt, extraction and even which MATH split it used were not checked in this audit. It cannot sit beside ours. The human baseline `0.9` (`:4147`) is one IMO medalist on 20 problems (paper, "Human-Level Performance"), not a harness.
- **eval.yaml counts the whole dataset.** `dataset_samples: 12500` (`inspect_evals:math/eval.yaml:12`) counts train plus test. The Task serves the 5,000-problem test split, which our row declares (`benchmarks.py:4157-4160`). eval.yaml's description also says the original dataset was taken down after a DMCA notice. The authors now point to [`qwedsacf/competition_math`](https://huggingface.co/datasets/qwedsacf/competition_math) (`fork:README.md:7`), a mirror this audit did not load. The authors' target rule reproduces every MATH-lighteval target (0 differ), but byte identity with the original 2021 tarball is unchecked.
- **One key cannot be matched by a one-line answer.** Case 4135's key `90\text{ square\nunits}` contains a newline. The `ANSWER:` pattern stops at the newline, so no reply can match it on exact match on either side (`differ 0`). This is a property of the reference, matched and not counted.
- **inspect's sympy check depends on `SIGALRM`.** `is_equiv_sympy` wraps parsing in `signal.signal(SIGALRM, …)` (`inspect_evals:math/utils.py:170-188`, `:197`). Off the main thread that raises, and the broad `except Exception` (`:228-230`) turns it into "not equivalent". In this audit, `grade_case` in a worker thread gave the sympy column 0/149 where the main thread gave 142/149. The headline is untouched (149/149). The shipped aggregate route on the main thread was correct (139/149 on Cases 1-149). The runner child drives its loop with `asyncio.run` on the main thread (`apps/screamingface-engine/src/screamingface_engine/runner/main.py:755`). The draft-feedback path's `_run_sync` uses a worker thread when a loop is already running (`single_shot.py:1612-1629`), but it reads the headline only. Not counted: no production path that grades the sympy Named Score off the main thread was found, and that was not proven end to end. A real run's sympy column at 0 with a non-zero headline would show it.
- **inspect_evals PRs #2199 and #2340 are open.** D1 adopts both. When a pin bump brings either fix, the tripwire `test_named_deviation_math.py:91` fails, D1 shrinks to our two steps, and this record goes stale.
