# MuSR — Fidelity Record

## Verdict

**`unverified`.** Our headline is plain accuracy over the 250 `murder_mysteries` Cases. It is built to sit beside a run of [inspect_evals v0.20.0 `musr`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/musr) with its defaults: the `regular` prompt, zero-shot, the `choice()` scorer and the `accuracy` metric. inspect_evals publishes no number for this eval. Our headline is **not** comparable to the paper's headline, GPT-4 80.4% on Murder Mystery with CoT+ (Table 5 of [Sprague et al., ICLR 2024, v2](https://arxiv.org/abs/2310.16049v2)), nor to its "Regular" row (GPT-4 64.8%, Table 7). The reason is that inspect_evals marks differently from the authors' harness. It asks for and parses a **letter**, while the harness asks for and parses a **choice number**, so on our answer sheets the two disagree on all 250 Cases for a reply in either format (Upstream notes, `unbounded`). Against inspect_evals, three things hold. (1) Every Case is served with inspect's exact text, key and options. (2) Our 4,000 sheet marks equal inspect's own solver and scorer on every sheet, and 750 more equal inspect's real `eval()` under `mockllm`. (3) The roll-up equals inspect's to four decimals on eight vectors. Two deviations are declared. D1, the forced row-shuffle seed, is cosmetic with bound 0. D2, the system message delivered as leading user text, is `possibly-score-changing` with bound `unknown`, so the rule gives `unverified`. Arithmetic: `bounds against inspect_evals = 0/250 (D1) + unknown (D2)`. One `possibly-score-changing` deviation is open, so the verdict is `unverified`. Once D2 is bounded at ≤ 0.005, the rule gives `comparable-to-inspect`, because inspect_evals vs the original harness is `unbounded`.

## Deviations

### D1 — row order forced by a declared shuffle seed

- **Declared.** The row comment at `apps/screamingface-engine/src/screamingface_engine_inspect/prepare.py:1132` ("Fold: order forced by shuffle_seed through inspect's shuffle (D1)") sits on the row `prepare.py:1137-1147`, with `shuffle_seed=20260922` at `:1145`. The mechanism is the D1 row of `docs/spec/2026-10-02-ome-1460-one-fetch-path.md:281`, and musr's line is at `:366`. The Benchmark description says "Cases are served in a fixed seeded shuffle" (`benchmarks.py:1066-1077`).
- **Where.** Ours: `fetch_pins_of(spec)` (`apps/screamingface-engine/src/screamingface_engine_inspect/task_replay.py:404-411`) forces the seed onto the eval's `hf_dataset(shuffle=True)`. Theirs: `inspect_evals:musr/musr.py:54`, `:68-74` (`shuffle=shuffle`, no seed), then `inspect_ai:dataset/_sources/hf.py:264-265`.
- **What differs.** Only the Case numbering. Ours is one fixed permutation (Case 1 is Hub row 39). inspect's is a fresh permutation on every run. Text, options and key are identical on all 250 Cases.
- **Severity / bound.** `cosmetic`, `0`. A Case's mark does not depend on its position: all 4,000 marks are identical (Checks run 5).

### D2 — the eval's system message rides inside the user prompt

- **Declared.** The row comment at `apps/screamingface-engine/src/screamingface_engine_inspect/prepare.py:1132-1133` says "inputs gain the eval's system message (D3)", where D3 is the spec's numbering. The spec's D3 row is at `docs/spec/2026-10-02-ome-1460-one-fetch-path.md:283`, its musr line at `:366`, and its accepted-risk bullet at `:259-262`. The plugin-level rule is at `capture.py:75-77` ("Named deviation (contracteval pattern): a Benchmark cannot address a Candidate's system role…"), and the glossary's Named Deviation names "a system message delivered as input text" (`CONTEXT.md:323-326`).
- **Where.** Ours: `SYSTEM_PROMPT + "\n\n" + user prompt` as one user text (`apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:79`, `:538`). The grader gets the same single user message (`scorer_adapter.py:634-635`). Theirs: `system_message(SYSTEM_PROMPT)` inserts a `ChatMessageSystem` (`inspect_evals:musr/musr.py:79`; `inspect_ai:solver/_prompt.py:46-70`). The harness sends `{'role': 'system'}` + user for OpenAI models (`fork:src/model/openai.py:207-208`; `fork:eval/eval.py:201`).
- **What differs.** Every byte of text is equal on all 250 Cases (Checks run 5, 6). The Candidate receives the line "You are a helpful assistant that will answer the questions given by the user." as the opening of the user turn, not as a system turn. The scorer never reads it, since `choice()` reads only the reply and the choices.
- **Severity / bound.** `possibly-score-changing`, `unknown`. A Candidate may follow a system instruction differently from user text. This needs a paired Candidate run over the 250 Cases (Recommended paid runs).

## Recommended paid runs

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `musr`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/musr) adapts its prompts from [Zayne-sprague/MuSR@b1f4d416](https://github.com/Zayne-sprague/MuSR/tree/b1f4d4168a9cfc6760e8b74d728e4516023dfaa5) (`prompts.py:195`) but changes three things.
  1. **Answer format and extraction.** inspect lists options as `A) name` and asks for "the choice letter" (`prompts.py:236`; `inspect_ai:solver/_multiple_choice.py:57-68`). It parses the last `ANSWER:` token as one letter and marks an unparseable reply wrong (`:98-152`). The harness lists `1 - name`, asks for "the choice number" (`fork:eval/eval.py:154`, `:165`), and credits a reply if the gold number appears anywhere in the last `answer:` line, checking gold first. Otherwise it picks a random choice (`:213-251`). On the sheets, a letter reply sends the harness to its random fallback on 250/250 Cases, and a number reply scores 1.0 under the harness and 0.0 under inspect on 250/250 Cases. `ANSWER: 1 or 2` scores 1.0 under the harness on every Case.
  2. **Prompt variant.** inspect defaults to `regular` (`musr.py:42`). The paper's headline (Table 5, GPT-4 80.4) and the only ablation the harness enables use `cot+` (`fork:eval/eval.py:50`). inspect's `cot+` hint (`prompts.py:201-209`) also breaks lines mid-sentence, where the harness's hint is one line per paragraph (`fork:eval/eval.py:43`). That template is not used by default.
  3. **Sampling.** The harness fixes `temperature=1.0, top_p=1.0, max_tokens=2400` for GPT-4 (`:38`). inspect fixes nothing.

  The gap depends on how a Candidate formats its reply, so it cannot be bounded without a run: `unbounded`. This is why the target verdict is `comparable-to-inspect` and not `comparable-to-paper`.
- **Harness vs paper.** The paper's Appendix I prompts and the harness's `cot+` prompt agree, both asking for "including the choice number". The paper reports Murder Mystery as 250 stories (Table 2), equal to the harness file and the Hub split. One harness quirk: `eval.py:43` loads `murder_mysteries.json`, but the committed file is `datasets/murder_mystery.json`. As committed, the script cannot find its data without a rename. Bound 0 on marks, recorded only.
