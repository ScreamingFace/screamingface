# SEvenLLM MCQ (English) — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline is plain accuracy over the 50 English multiple-choice questions of [SEvenLLM-Bench](https://huggingface.co/datasets/Multilingual-Multimodal-NLP/SEVENLLM-Dataset/tree/1de23ce55cadc984d3f3a7b52c4035a68c6cd5b0). It sits beside a run of [inspect_evals v0.20.0 `sevenllm_mcq_en`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/sevenllm): `prompt_template(TEMPLATE)` + `multiple_choice()`, the `choice()` scorer, `accuracy`. inspect_evals publishes no number for this eval.

Against inspect_evals, everything matches:
- every Case's text is byte-equal to the single user message inspect's own solver chain and its real `eval()` send (no system message on either side);
- the gold letters, options, question and passage equal the pinned file row by row, in file order;
- our 1,400 marks equal inspect's solver + `choice()` on all 28 sheets;
- the roll-up equals to four decimals on 5 vectors.

Our headline is **not** comparable to the paper's Table 6 ([Ji et al. 2024, v2](https://arxiv.org/abs/2405.03446v2)). The authors' code ([CSJianYang/SEevenLLM@a807d678](https://github.com/CSJianYang/SEevenLLM/tree/a807d67853b36bd9a491e70da83a40d0e74e49d3)) marks a different exam. Its prompt has no `ANSWER:` instruction, and its extractor credits a reply only when it holds exactly one capital A–D, so every `ANSWER: X` reply scores 0 there. On the authors' own recorded replies the two examiners disagree on 44–48 of 50 Cases per model (harness 44–48/50, inspect 0/50). That gap is `unbounded` (Upstream notes).

Arithmetic: bounds against inspect_evals = `0/50 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`. inspect_evals vs the original harness = `unbounded` > 0.005. Rule (spec §2.3) → `comparable-to-inspect`.

Qwen models get the same text wrapped in chat tokens (`:27-31`, `:113-114`). inspect_evals writes its own `TEMPLATE` ("inspired from the inference work done by the authors", `inspect_evals:sevenllm/sevenllm.py:39-49`), puts the question and passage under it, and `multiple_choice()` wraps all of it in `SINGLE_ANSWER_TEMPLATE` with the options listed as `A) …` lines and the instruction to answer `'ANSWER: $LETTER'`.
  2. **Answer extraction.** The harness credits a reply only if it is one A–D character, or a longer string holding exactly one capital A, B, C or D anywhere (`fork:code/score/get_score_choice.py:31-36`). So `ANSWER: B` counts two capitals (the "A" of ANSWER and the B) and is marked unknown, i.e. 0. inspect requires an `ANSWER:` line (`inspect_ai:solver/_multiple_choice.py:98-110`), so a bare `B` is 0 there.
  3. **The two instructions inside inspect's prompt contradict each other.** inspect's eval `TEMPLATE` says "return just the option letter and not the entire text" (`inspect_evals:sevenllm/sevenllm.py:44-45`), and the wrapper it sits in says to answer `'ANSWER: $LETTER'`. A Candidate that obeys the inner instruction scores 0 (sheet bare `X`: inspect 0/50). We replay this faithfully; it is inspect_evals' design and worth reporting to them.

  On the answer sheets the two examiners disagree on 50/50 Cases for nine reply shapes and on 23/50 and 3/50 for two more (Checks run 4). On the authors' own 12 recorded reply sets the harness gives 44–48/50 and inspect gives 0/50, because every recorded reply is a bare letter. How often a given Candidate writes one shape or the other cannot be bounded without a run: `unbounded`. This gap is why the verdict is `comparable-to-inspect`, not `comparable-to-paper`.
