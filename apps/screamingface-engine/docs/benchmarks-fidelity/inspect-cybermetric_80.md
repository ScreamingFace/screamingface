# CyberMetric-80 — Fidelity Record

## Verdict

**`unverified`.** Our headline is plain accuracy over the 80 CyberMetric-80 questions. It is built to sit beside a run of [inspect_evals v0.20.0 `cybermetric_80`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric), which uses `system_message` + `multiple_choice()`, the `choice()` scorer and the `accuracy` metric. inspect_evals publishes no number for this eval. Our headline is **not** comparable to the paper's Table III (GPT-4o 96.25% on 80 Q, [Tihanyi et al. 2024, v2](https://arxiv.org/abs/2402.07688v2)). inspect_evals itself marks differently from the authors' released evaluator ([cybermetric/CyberMetric@205262cd `CyberMetric_evaluator.py`](https://github.com/cybermetric/CyberMetric/tree/205262cdf5022ba890e792efd176fb19d42913fa)): the prompt text differs, the evaluator takes the first `ANSWER:?\s*[A-D]` anywhere in the reply where inspect takes the last `ANSWER:` line, and the evaluator re-asks the model up to 5 times when it finds no answer. Also, 13 of the 80 questions were edited after the paper's number was produced. On the answer sheets the two examiners disagree on all 80 Cases for four reply shapes, so that gap is `unbounded` (Upstream notes).

Against inspect_evals, the following match:
- every Case's text (system text + blank line + user prompt) is byte-equal to what inspect's own solver chain and its real `eval()` send;
- the gold letters and options equal the pinned file row by row;
- our 1,280 marks equal inspect's solver + `choice()` on every sheet;
- the roll-up equals to four decimals on 5 vectors.

One deviation remains open. D1: the system message arrives as user text, not as a system turn. It is `possibly-score-changing`, bound `unknown`. By rule (spec §2.3), an open `possibly-score-changing` deviation means `unverified`. The bounds against inspect_evals that are known sum to `0/80 = 0.0000`, plus D1 `unknown`. inspect_evals vs the original harness is `unbounded`, so once D1 is bounded at `0/80` the verdict becomes `comparable-to-inspect`.

## Deviations

### D1 — the eval's system message rides inside the user prompt

- **Undeclared on the row; declared at the plugin level** (a finding for the row). The fold is declared at the plugin level in `apps/screamingface-engine/src/screamingface_engine_inspect/capture.py:75-79` ("Named deviation (contracteval pattern): a Benchmark cannot address a Candidate's system role, so the eval's system instruction rides ahead of the user prompt"). The glossary's Named Deviation names "a system message delivered as input text" (`CONTEXT.md:325`). The row has no `# NAMED DEVIATION` line: neither `benchmarks.py:2861-2922` nor `prepare.py:376-388` has one. The row's description says the Cases are "asked with the eval's own system message" (`benchmarks.py:2866-2867`) but does not say the message arrives as user text. This row is also not one of the spec's D3 rows (`docs/spec/2026-10-02-ome-1460-one-fetch-path.md:259-262` names musr and xstest only). One `# NAMED DEVIATION` line on the row would make D1 declared. It would stay counted in the bound.
- **Where.** Ours: `SYSTEM_MESSAGE + "\n\n" + user prompt` as one user text (`capture.py:79`, `:538`). The grader receives the same single user message (`scorer_adapter.py:635`). Theirs: `system_message(SYSTEM_MESSAGE)` (`inspect_evals:cybermetric/cybermetric.py:35`, `:77`) inserts a `ChatMessageSystem` (`inspect_ai:solver/_prompt.py:46-70`). The harness also sends `{"role": "system"}` + user (`fork:CyberMetric_evaluator.py:31-34`).
- **What differs.** The text is equal on all 80 Cases, byte for byte (Checks run 4, 6). The Candidate gets "You are a security expert who answers questions." as the opening of the user turn, not as a system turn. The scorer never reads it: `choice()` reads only the reply and the choices.
- **Severity / bound.** `possibly-score-changing`, `unknown`. A Candidate may follow a system instruction differently from user text. Measuring that needs a paired Candidate run over the 80 Cases (Recommended paid runs). With 80 Cases, one differing mark is 1/80 = 0.0125, which is above the 0.005 tolerance. So D1 only clears the tolerance if the run shows 0 differing Cases.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `cybermetric`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/cybermetric) departs from the authors' evaluator [cybermetric/CyberMetric@205262cd `CyberMetric_evaluator.py`](https://github.com/cybermetric/CyberMetric/tree/205262cdf5022ba890e792efd176fb19d42913fa) on three dimensions:
  1. **Prompt.** inspect wraps the eval's `Question: …\nOptions: A) …, B) …, …\n\n` text in inspect_ai's `SINGLE_ANSWER_TEMPLATE`. Because `record_to_sample` sets `choices` to the option *letters* (`inspect_evals:cybermetric/cybermetric.py:119`), the template then appends `A) A\nB) B\nC) C\nD) D` (`inspect_ai:solver/_multiple_choice.py:57-68`), so the options appear once in full and once as bare letters (Case 1, Checks run 4). The harness sends the same question and options followed by `Choose the correct answer (A, B, C, or D) only. Always return in this format: 'ANSWER: X' ` (`fork:CyberMetric_evaluator.py:25-26`). The system text is the same on both sides.
  2. **Answer extraction.** The harness takes the *first* `ANSWER:?\s*([A-D])` anywhere in the reply, case-insensitive, colon optional (`fork:CyberMetric_evaluator.py:19`). inspect requires the colon and takes the *last* match (`inspect_ai:solver/_multiple_choice.py:98-115`).
  3. **Retries.** When the harness finds no letter, it re-asks the model up to 5 times (`fork:CyberMetric_evaluator.py:24`, `:27-41`). inspect marks that Case 0 after one call.

  On the sheets, the two examiners disagree on 80/80 Cases for four reply shapes (Checks run 4), and on 20/80 for `Answer: Because …`, where the harness's case-insensitive `[A-D]` reads the "B" of "Because" as the letter B. How often this happens depends on how a Candidate formats its replies, so it cannot be bounded without a run: `unbounded`. This gap is why the verdict, once D1 is bounded, would be `comparable-to-inspect` rather than `comparable-to-paper`.
- **Harness vs paper: the released evaluator is a showcase script, not the 25-model run.** The README calls it "a compact Python script … to showcase how to utilize the Dataset with OpenAI GPT" (`fork:README.md:49`). It hard-codes `gpt-3.5-turbo-0125` (`:30`) and sets no sampling parameters. The paper ran 25 models, open ones on an AWS ml.p4d.24xlarge, at "temperature of 1.0, top_p at 0.9, and top_k at 50" (§IV-A), and gives no prompt text. The evaluator is the only released code, so it is the reference; whether every Table III number used its prompt and its retry rule is not stated. The paper itself warns of "up to 3-4 percentage points" run-to-run variance (§IV-A).
- **The questions changed after the paper's number.** The CyberMetric-80 file at the paper's time (`47b6443`, 2024-02-15; paper v2 2024-06-03) differs from the pin both inspect_evals and we read (`205262cd`, 2024-12-18, "Questions fix") on 13 of 80 rows (Checks run 8):
  - row 7 reorders its options and moves the key from B to C;
  - row 36 rewrites its question and options;
  - row 64 rewrites its question;
  - the other 10 drop trailing periods from options.

  Table III's GPT-4o 96.25% and the catalogue's `frontier_score=0.9625` (`benchmarks.py:2914-2919`) were measured on the older file. Bound of the dataset change alone, vs the paper: up to 13/80 = 0.1625 (3/80 = 0.0375 for the rows whose meaning or key changed).
- **A later upstream commit does not change the rows.** `294662b` (2026-05-27, "Update CyberMetric-80-v1.json") changes the file's sha256 but no row's question, options or solution. The pin is unaffected. Bound 0.
