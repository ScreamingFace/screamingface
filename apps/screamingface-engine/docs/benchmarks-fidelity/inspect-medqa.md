# MedQA (USMLE) — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline is plain accuracy over the 1,273 five-option USMLE test questions. It can sit beside a run of [inspect_evals v0.20.0 `medqa`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/medqa): zero-shot `ANSWER: $LETTER` template, `choice()` scorer, `accuracy` metric (its README reports gpt-4.1 87.4% and gpt-4o-mini 68.5%). Every dimension matches inspect_evals: the same 1,273 Cases in the same order, sealed by both digests. All 1,273 Candidate inputs are byte-identical to the eval's own solver output. 17,822 of 17,822 answer-sheet marks are equal, and the roll-up is equal to four decimals on 18 vectors. The result: `sum of bounds against inspect_evals = 0/1273 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`.

Ours is **not** comparable to the paper ([Jin et al. 2020, arXiv 2009.13081v1](https://arxiv.org/abs/2009.13081v1), headline BioBERT-Large 36.7% test), because inspect_evals is a different exam from the authors' own. The authors report results on the **4-option** file: "we reported results for 4 options in the paper" (`fork:README.md:21`; paper Table 3 "# of options per question 4", Table 8 CHANCE 25.0). inspect_evals loads the 5-option `test.jsonl`. The question text and gold answer text are the same on all 1,273 Cases, but every Case shows one extra distractor, and on 600 of 1,273 the gold letter moves. Also, the authors' systems are retriever-plus-reader models with no prompt and no reply reader. So: `inspect_evals vs original harness: dataset 1273/1273 = 1.0000 > 0.005, prompt and answer extraction unbounded` → `comparable-to-inspect` (Upstream notes U1, U2).

**Caveat for the Leaderboard:** the row's `frontier_score` (o1-preview 0.96) is a **MedQA (US 4-option)** number, by the row's own comment and by Table 1 of its source. Our Cases are 5-option, so that reference line comes from a different exam (U3).

[jind11/MedQA@27b02f66](https://github.com/jind11/MedQA/tree/27b02f66aac217933c9648a06f82e9f720377925) says "we also include the '4_options' version … since we reported results for 4 options in the paper" (`fork:README.md:21`). The paper says it deleted one wrong option per USMLE question (§3.2; Table 3 "4"; Table 8 chance 25.0). [inspect_evals v0.20.0 `medqa`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/medqa) loads `med_qa_en_bigbio_qa` → `US/test.jsonl`, which has 5 options (`inspect_evals:medqa/huggingface_artifact/med_qa.py:192`). The 4-option file sits beside it in the same archive (`:225`, config `med_qa_en_4options_bigbio_qa`). The two files hold the same 1,273 questions in the same order with the same gold answer text. Every 4-option row's options are a subset of the 5-option row's. But every Case shows one more distractor (chance 20% vs 25%), and the gold letter moves on 600 of 1,273 (Checks run 5). A Candidate's score on our Cases is therefore expected to sit **below** its score on the paper's exam. How far below cannot be bounded without runs on both.
- **U2: the harness has no prompt and no reply reader.** The bound is `unbounded`, inspect_evals vs harness. The released code is the IR baseline: a BM25 score for each question+option pair, then argmax (`fork:IR/aristomini/solvers/textsearch.py:29-56`). The paper's headline readers (BioBERT-Large 36.7% test, Table 8) are fine-tuned on retrieved context, and **their code is not in the repo** (34 files, `IR/` only). inspect_evals supplies a zero-shot `ANSWER: $LETTER` template and inspect's `ANSWER:` regex. On the sheets, a reply that names the right option any other way (bare `C`, `(C)`, `The answer is C.`, the option's text) scores 0 on inspect and on ours (Checks run 6). The authors' systems can never "fail to answer". The per-Case rule (letter == `answer_idx`) and the pooled accuracy are the same on both (metric and roll-up rows).
- **U3: the row's reference lines come from other exams.** The `frontier_score` 0.96 (o1-preview) is Table 1 "MedQA (US 4-option)" of [Nori et al. 2024](https://arxiv.org/html/2411.03590v1), and the row's own comment says "MedQA US 4-option test set" (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2667-2671`). It was measured on U1's 4-option Cases, with that paper's own prompt and reader, so it is a different exam from our 5-option Cases. The `human_baseline` 0.87 (`benchmarks.py:2666`; `inspect_evals:medqa/eval.yaml:14-17`) is the "Human expert" figure in [Tian et al. 2023 v2](https://arxiv.org/abs/2306.10070v2), Figure 2, cited there to its reference [31]. The inspect_evals README describes it as the real USMLE's 95th percentile (`inspect_evals:medqa/README.md:71`), not a score measured on these Cases. This audit changes neither. It records that neither number is comparable to a score on our Cases.
- **U4: the harness was not run.** It needs Python 3.6, an Elasticsearch 2.4.1 server and the indexed textbook corpus (`fork:README.md:31-55`), and it produces predictions rather than marking supplied ones. Its marking expression (`textsearch.py:69`, `:73`) was re-run over the sheets' selected letters instead (metric, roll-up). That is a source comparison, not an execution.
- **U5: wording nits in inspect_evals' template, cosmetic, bound 0.** `TEMPLATE` says "given the context" though the Sample carries no context (`inspect_evals:medqa/medqa.py:28`; the loader sets `context = ""`, `med_qa.py:283`). It also lacks a space in `'ANSWER: $LETTER'(without quotes)` (`medqa.py:29-30`). Ours carries both byte for byte (prompt row). They are listed so a reader of Case 1 is not surprised.
- **inspect_evals' own published numbers:** "Results from July 3, 2025, running on all 1,273 samples": gpt-4o-mini 68.5%, gpt-4.1 87.4% (`inspect_evals:medqa/README.md:90-95`). Its README also cites GPT-4 at 86.1% from [arXiv 2207.08143](https://arxiv.org/abs/2207.08143) (`:5`); this audit did not check which option variant that number used.
- **Harness vs paper.** No disagreement found: both say 4 options and 1,273 USMLE test questions. The authors' Google Drive archive is byte-identical to the pinned Hub `data_clean.zip` (Checks run 5).
