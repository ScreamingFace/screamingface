# SEvenLLM MCQ (Chinese) — Fidelity Record

## Verdict

**`comparable-to-inspect`.** Our headline is plain accuracy over the 50 Chinese multiple-choice questions of [SEvenLLM-Bench](https://huggingface.co/datasets/Multilingual-Multimodal-NLP/SEVENLLM-Dataset/tree/1de23ce55cadc984d3f3a7b52c4035a68c6cd5b0). It is comparable to a run of [inspect_evals v0.20.0 `sevenllm_mcq_zh`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/sevenllm) (`prompt_template(TEMPLATE)` + `multiple_choice()`, the `choice()` scorer, the `accuracy` metric). inspect_evals publishes no number for this eval. Against inspect_evals, every dimension matches:

- every Case's input is byte-equal to the single user message inspect's own solver chain and its real `eval()` send (50/50, no system message, so no fold);
- ids, gold letters and options equal the pinned Hub file row by row, in file order;
- our 1,550 marks equal inspect's solver + `choice()` on all 31 sheets, including the authors' 12 recorded reply files;
- the roll-up equals to four decimals on 5 vectors.

Our headline is **not** comparable to the paper's Table 6 ([Ji et al. 2024, v2](https://arxiv.org/abs/2405.03446v2)). inspect_evals is a different examiner from the authors' scorer ([CSJianYang/SEevenLLM@a807d678 `code/score/get_score_choice.py`](https://github.com/CSJianYang/SEevenLLM/tree/a807d67853b36bd9a491e70da83a40d0e74e49d3)): the authors credit a reply that contains exactly one uppercase `A`–`D` character, and inspect requires an `ANSWER: X` line. On the authors' own recorded replies, the authors' rule reproduces the paper's Zh column on all 6 SEvenLLM rows (47–49/50), and inspect marks every one of those files 0/50 (Upstream notes). By rule (spec §2.3): `sum of bounds against inspect_evals = 0/50 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`; `inspect_evals vs the original harness = unbounded` (≥ 47/50 = 0.94 differing marks per recorded reply file, > 0.005) → `comparable-to-inspect`.

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `sevenllm`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/sevenllm) departs from the authors' code ([CSJianYang/SEevenLLM@a807d678](https://github.com/CSJianYang/SEevenLLM/tree/a807d67853b36bd9a491e70da83a40d0e74e49d3)) on two dimensions:
  1. **Prompt.** The authors send an Alpaca prompt, `### Instruction:\n{instruction}\n\n### Input:\n{input}\n\n### Response:` (`fork:infer.py:22-26`; a Qwen chat-tag variant `:27-31`), where `{instruction}` renders the row's question-and-choices dict as Python dict text (Checks run 8). inspect wraps the question and input in the eval's own `TEMPLATE` (`inspect_evals:sevenllm/sevenllm.py:42-49`, "inspired from" `infer.py`, `:39-41`) and then in inspect_ai's `SINGLE_ANSWER_TEMPLATE`, with the options as `A) …` lines (Case 1, Checks run 4).
  2. **Answer extraction.** The authors accept a reply that contains exactly one uppercase `A`–`D` character anywhere, or is one such character (`fork:code/score/get_score_choice.py:31-45`). inspect requires an `ANSWER: X` line (`inspect_ai:solver/_multiple_choice.py:98-110`). The two rules are close to disjoint: `ANSWER: B` holds the `A` of "ANSWER", so the authors' rule rejects every `ANSWER:` reply, and inspect rejects every bare letter.

  Evidence with real replies: on the authors' 12 recorded reply files (Checks run 5), the authors' rule gives 47–49/50, and it reproduces the paper's Table 6 Zh sums on all 6 SEvenLLM rows (49, 48, 48, 49, 47, 49; Checks run 10). inspect marks every file 0/50, because the models answered with a bare letter. On the synthetic sheets the examiners disagree on 50/50 Cases for 12 of 19 reply shapes (Checks run 4). How large the gap is for a given Candidate depends on how it formats its reply, so it cannot be bounded without a run: `unbounded`.
- **inspect's own prompt gives two answer formats.** The eval's inner `TEMPLATE` says "If you are given options (A, B, C, D), return just the option letter and not the entire text" (`inspect_evals:sevenllm/sevenllm.py:44-45`), and the outer multiple-choice template asks for `'ANSWER: $LETTER'` (`inspect_ai:solver/_multiple_choice.py:18`). `choice()` marks a bare letter 0: the bare-`X` sheet gives 0/50 through inspect's solver chain and 0.0000 through inspect's real `eval()` (Checks run 4, 6). A Candidate that follows the inner instruction loses every mark. We mirror inspect byte for byte, so this is inspect_evals behaviour, not ours; it is part of the unbounded gap above, and an inspect_evals issue may be worth filing.
- **Harness vs paper.** The paper says the MCQ outputs "were manually verified" (§3.2). The released scorer cannot run as written on the released data: it keeps only rows whose `task` field ends in `choice` (`fork:code/score/get_score_choice.py:14`), and neither the Hub `test.jsonl` nor the repo's result files carry a `task` field (Checks run 4, 8), and its test path `./data/test.jsonl` (`:65`) is not in the repo. It also sums ids `1201`–`1300` (`:99-100`), both languages together, where the paper reports each language. This audit applied its per-reply rule (`:25-47`) and exact match (`:84`) to the 50 zh rows by id. Because that rule reproduces all 6 published Zh sums, the manual check changed no mark on those rows. Bound 0 for this note.
- **Sampling.** The authors decode greedily (`do_sample` default `False`, `fork:infer.py:250`, `:312`; `temperature` commented out `:249`) with `max_new_tokens=2000` (`:252`); the paper does not state sampling for the MCQ table. Neither inspect_evals nor we fix a value.
- **The dataset has not changed since the paper.** `test.jsonl` at the Hub upload commit `7a42e0ca` (2024-05-06, the day paper v1 was submitted) and at the pin `1de23ce5` are byte-identical (Checks run 9). Bound 0.
- **No published inspect_evals number and no frontier number.** The eval's README has no results section (`inspect_evals:sevenllm/README.md`, 113 lines). Table 6 covers 7B–14B chat models and the authors' fine-tunes only, reported as counts out of 50 per language. "Comparable-to-inspect" means comparable to a run of the pinned eval, not to a number inspect_evals printed.
