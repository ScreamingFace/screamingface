# HealthBench Professional — Fidelity Record

## Verdict

**`not-comparable`.** Our headline is the clipped mean of the **unadjusted** per-Case rubric scores. The [paper's](https://arxiv.org/abs/2604.27470v1) primary score, and both published numbers on our row (human physicians 0.437, GPT-6 Astra 0.647 "length-adjusted"), use the **length-adjusted** per-Case score instead: s_len = s − 2.94×10⁻⁵ × (answer chars − 2,000) (paper p.8 §4.1). [simple-evals' `--healthbench-professional-mode`](https://github.com/openai/simple-evals/blob/652c89d0ca9df547706735883097e9537d40dc47/simple_evals.py) refuses to run unless that adjustment is switched on. Everything else that can be checked for free matches simple-evals at `652c89d`. The Candidate gets the Hub conversation byte for byte on all 525 Cases. All 27,240 judge prompts match by sha256. The unadjusted per-Case score matches on all 12,600 answer sheets. The clipped-mean roll-up matches to four decimals on all 10 vectors. The adjustment, though, applies to every Case whose answer is not exactly 2,000 characters, and its size depends on the Candidate's answer lengths. It differed on 525 of 525 Cases in the answer sheets. So D1 is `score-changing` with bound `unbounded`, and the rule gives `not-comparable` before any sum is taken. Its headline effect is −2.94×10⁻⁵ × (mean answer chars − 2,000). That stays inside the tolerance only while a run's mean answer length is between 1,830 and 2,170 characters. A 4,000-character mean shifts the headline by −0.059. Two more facts each lead to `not-comparable` on their own. First, the judge is a floating `openrouter/openai/gpt-5.4` sent without the paper's `reasoning_effort="low"`, so the examiner differs from the one the paper used (D2). Second, the dataset card says the published numbers came from OpenAI's internal implementation, not simple-evals (Upstream notes). `bounds vs original harness: D1 = unbounded → not-comparable` (D4 = k/525 per run; D2 and D3 = unknown, paid run below).

## Deviations

### D1 — no length adjustment on the per-Case score

- **Undeclared.** Nothing in the package, its README, or the row mentions length adjustment, except the row's own frontier-score comment, `# Frontier score: HealthBench Professional rubric score, length-adjusted.` (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:4907`). That comment confirms the number shown beside our headline is adjusted. The row's description goes further and claims the headline "lines up with published HealthBench numbers" (`benchmarks.py:4831`).
- **Where.** Ours: the per-Case score is `case_score`, earned over winnable points (`apps/screamingface-engine/src/screamingface_engine_inspect/local_tasks/healthbench/scoring.py:22-76`), and nothing else (`healthbench.py:328-343`). Theirs: `calculate_length_adjusted_score` (`fork:healthbench_eval.py:157-164`) fills `overall_score_length_adjusted` whenever the adjustment is configured (`fork:healthbench_eval.py:440`). `--healthbench-professional-mode` refuses to run without both adjustment flags (`fork:simple_evals.py:72`, `:140`). The paper calls this "the primary score we report" (p.8 §4.1), with the coefficient 2.94×10⁻⁵ per character (0.0147 per 500 characters) and the 2,000-character centre. It is applied per example and then mean-and-clipped (p.9).
- **What differs.** Each Case's mark moves by −2.94×10⁻⁵ × (len(answer) − 2,000), so the headline moves by about −2.94×10⁻⁵ × (mean answer length − 2,000) before the clip. The 0.437 human baseline and the 0.647 frontier score on our row are adjusted numbers; ours is not.
- **Severity / bound.** `score-changing`, `unbounded`. Every Case is affected unless its answer is exactly 2,000 characters (525 of 525 differed in the answer sheets), and the size depends on the Candidate. It stays within 0.005 only while a run's mean answer length is 1,830–2,170 characters. The physicians' own answers average 2,142.8 characters, which shifts their headline by −0.0042. The paper reports that going from low to medium verbosity added about 1,300 characters (p.12), about −0.038.
- **Evidence.** Checks run 9-12. No paid run is needed to measure it: the adjustment depends only on answer lengths, which every recorded run already holds.

### D2 — judge: floating `gpt-5.4` slug, no `reasoning_effort="low"`, a 4096-token cap

- **Partly declared.** The slug is declared: the README says "The judge is `openrouter/openai/gpt-5.4` (the official judge is an OpenAI-internal snapshot we cannot reach)" (`local_tasks/healthbench/README.md:60-63`), and the row comment says "OpenRouter routes the floating slug (a named deviation, as hand-built)" (`benchmarks.py:4848-4850`). The 4096 cap is declared as "an Engine-side safety cap the official judge does not send" (`benchmarks.py:4852-4856`). The missing `reasoning_effort="low"` is **undeclared**. The row comment names it as the official judge's setting (`benchmarks.py:4848-4849`), but the pinned params are only `web_search=false, max_tokens=4096` (`benchmarks.py:4851-4860`; Checks run 4).
- **Where.** Theirs: `ResponsesSampler(model="gpt-5.4-2026-03-05", reasoning_model=True, reasoning_effort="low")` (`fork:simple_evals.py:338-346`). It sends `reasoning={"effort": "low"}` and no `max_output_tokens` (`fork:sampler/responses_sampler.py:63-73`). The paper says "the default grader is GPT-5.4 at low reasoning" (p.9 §4.1).
- **What differs.** The snapshot is not pinned on our side, so OpenRouter decides which gpt-5.4 answers. The reasoning effort is the provider's default, not `low`. A reply can also be cut off at 4096 output tokens, reasoning included, where the reference sets no cap.
- **Severity / bound.** `possibly-score-changing`, `unknown`. Only a paid re-grade can say how often the verdicts differ (Recommended paid runs). It also counts toward `not-comparable` on its own under spec §2.3: the grader is configured differently from the one the paper's number used.

### D3 — judge reply: a more lenient parser and a 2-redraw budget

- **Undeclared as a difference.** The README describes our rule, "anything else is redrawn (twice at most …) and a line that still has no verdict fails the whole Case" (`README.md:45-47`). It never says the reference differs.
- **Where.** Ours: `parse_verdict` through the shared `parse_judge_evidence` (`healthbench.py:222-237`, `VERDICT_FORMAT` at `:93`) and `MAX_JUDGE_REDRAWS: Final[int] = 2` (`apps/screamingface-engine/src/screamingface_engine_inspect/judge_redraw.py:38`). Theirs: `parse_json_to_dict` removes only a leading ```` ```json ```` fence and a trailing ```` ``` ```` before `json.loads` (`fork:healthbench_eval.py:100-108`), and then retries `while True` until `label is True or label is False` (`fork:healthbench_eval.py:415-423`).
- **What differs.** 7 of 20 synthetic reply shapes. Four shapes are a verdict for us but a redraw for them: a bare ```` ``` ```` fence, a fence followed by trailing text, an upper-case ```` ```JSON ```` fence, and a reply with text before the fence. Prose before the JSON is a verdict for us (False) and a redraw for them. Two JSON objects in one reply: we take the first; they redraw. A bare `true`: we redraw; the harness crashes with `TypeError` at `"criteria_met" in grading_response_dict` (`fork:healthbench_eval.py:419`). On all 268 real judge replies the verdicts are identical. Separately, after 3 unparseable asks we fail the Case as `judge_reply_invalid`; the harness never gives up.
- **Severity / bound.** `possibly-score-changing`, `unknown`. Where they differ, the harness takes a fresh draw instead of our verdict, so marks differ only to the extent a fresh draw would. Each run's `judge_redraws` and `judge_reply_invalid` counts show how often this happened.

### D4 — a Case that cannot be graded leaves the mean

- **Not a Named Deviation.** It follows the row's `failure_policy="coverage_declare"` (`benchmarks.py:4839`), and the Report states coverage beside the headline. None of the declared forms the rules list cover it.
- **Where.** Ours: a Case whose Candidate call fails, or whose judge gives no verdict on some line after its redraws, is left out of the clipped mean (pinned by `test_the_run_headline_is_the_hand_built_one`, `tests/unit/inspect/test_local_task_healthbench.py:321`, the run with `scored_cases == 4`). Theirs: every example is graded. The sampler retries any exception forever and turns a `BadRequestError` into an empty answer that is still graded (`fork:sampler/responses_sampler.py:86-100`). The judge loop never gives up (`fork:healthbench_eval.py:415`).
- **Severity / bound.** `score-changing`, bound `k/525` for a run with k failed Cases, which the run's Report lists. It is 0 at full coverage. For scale: the recorded worst-30 Fusion run (the sibling Benchmark) lost 33 of 157 Cases, all to Candidate `upstream_error`.
- **Related, Fusion only.** An abstaining Fusion's Case is scored 0.0 even when the judge rated its empty answer (`test_an_abstained_case_costs_one_case_at_zero_though_the_judge_still_rates_it`, `tests/unit/inspect/test_local_task_healthbench.py:380`). The harness has no notion of abstaining. A single-model Candidate never takes this path.

## Upstream notes

- **The published numbers did not come from simple-evals.** The dataset card at `349962fd` says OpenAI used "an internal evaluation implementation … and do[es] not release an official external implementation". It calls [simple-evals](https://github.com/openai/simple-evals/tree/652c89d0ca9df547706735883097e9537d40dc47) a "reference implementation" with "an option to use settings matching our internal implementation" and an "unofficial external implementation". `fingerprint.harness_url` is therefore the closest public code, not the code that produced the paper's numbers. The gap between them cannot be measured from outside: bound `unknown`.
- **Paper vs harness, samples per example.** For its main comparisons the paper averages 8 samples per example (p.9 §4.2). simple-evals defaults to `n_repeats=1` (`fork:simple_evals.py:394`), and the paper itself uses 1 sample for its verbosity and reasoning sweeps. The harness wins, so `sampling` is a match. Averaging 8 samples narrows run-to-run noise but leaves the expected headline unchanged, apart from the clip. Bound 0 on the expectation.
- **Paper vs harness, length adjustment: they agree.** `--healthbench-professional-mode` requires both adjustment flags (`fork:simple_evals.py:140`) and computes the paper's linear formula (`fork:healthbench_eval.py:164`). The CLI carries no default coefficient, so a user must pass `--healthbench-length-adjustment-center 2000 --healthbench-length-adjustment-penalty-per-500-chars 0.0147` from the paper. The harness's top-level `score` key, which its merge table prints (`fork:simple_evals.py:515`), is the **unadjusted** clipped mean. The adjusted number sits in `metrics["overall_score_length_adjusted"]`, so a reader of the harness's own summary table sees the unadjusted number. Bound 0 on what is computed.
- **The harness cannot read the Hub file as published.** `HealthBenchEval` expects `prompt`, `rubrics[].criterion`/`points`/`tags`, `example_tags` and `prompt_id` (`fork:healthbench_eval.py:332-335,497,516-517,550`). The Hub file uses `conversation.messages` and `rubric_items[].criterion_text`/`points`, so a conversion is needed, and simple-evals ships none. This audit used a field-rename shim (Checks run 8).
- **Harness bug on a bare JSON scalar.** A judge reply such as `true` makes `parse_json_to_dict` return a bool, and `"criteria_met" in grading_response_dict` then raises `TypeError` (`fork:healthbench_eval.py:419`), which ends that example's grading. Ours redraws. None of the 268 real replies hit this.
- **Candidate system message in the harness.** simple-evals' chat-completion model entries add `OPENAI_SYSTEM_MESSAGE_API` (`fork:simple_evals.py:216`, …). That message then appears in the judge's transcript, because the transcript is built from `actual_queried_message_list` (`fork:healthbench_eval.py:507`). Its reasoning-model entries add none, and the paper uses "default system message settings". Ours never adds one, which matches the paper.
- **A private held-out set exists.** The card says OpenAI keeps "a small private held-out set". The 525 public rows are what everyone, ours included, can run.
- **[inspect_evals' `healthbench`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/healthbench) (v0.20.0) is not a reference here.** The README (`local_tasks/healthbench/README.md:17-19`) says it reads the original HealthBench, not Professional, and that its judge sends temperature 0.0 and a system message.
