# AGIEval SAT-Math — Fidelity Record

## Verdict

**`unverified`.** On grading, our AGIEval SAT-Math is the same examiner as [inspect_evals v0.20.0 `agie_sat_math`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/agieval): plain accuracy over all 220 questions of [ruixiangcui/AGIEval `data/v1_1/sat-math.jsonl` at `84ab72d9`](https://github.com/ruixiangcui/AGIEval/tree/84ab72d94318290aad2e4ec820d535a95a1f7552). The Case Digest and Case Set Digest reproduce, all 220 prompts are byte-identical to inspect's own `multiple_choice` render, and our 3,740 marks equal inspect's solver-plus-`choice()` marks on every one of 17 answer sheets. The roll-up equals to four decimals on eight vectors. What blocks a verdict is the Candidate's sampling. inspect_evals' Task fixes `GenerateConfig(temperature=0, max_tokens=2048, top_p=1)`, citing the paper's §4.2.4. Our importer never reads `task.config`, and this row neither applies nor declares the drop (D1). That gap can change the Candidate's replies, but only a paid run can bound it, so it is `possibly-score-changing` with bound `unknown`. Arithmetic: `sum of bounds against inspect_evals (grading dimensions) = 0/220 = 0.0000 ≤ COMPARABLE_TOLERANCE (0.005)`, but D1 is open, so the result is `unverified`. Even with D1 settled, the record could not say `comparable-to-paper`. inspect_evals and the authors' harness are different examiners: a one-shot `ANSWER: $LETTER` prompt graded by the `ANSWER:`-line regex, against a two-call prompt graded by the first capital letter A–F of the second reply. On a reply in the harness's own style (` D.`), the two disagree on all 220 Cases (`unbounded`, Upstream notes). The paper's headline (GPT-4 95.0 zero-shot CoT, Table 2) comes from that other examiner.

## Deviations

### D1 — inspect_evals' fixed Candidate sampling is not applied

- **Undeclared.** The row (`apps/screamingface-engine/src/screamingface_engine_inspect/benchmarks.py:2318-2376`) carries no Named Deviation comment, no `params`, and no description sentence about generation settings. Its description (`:2322-2329`) is silent on sampling. A precedent row declares the same drop: MATH's "Named Deviation: the Task's config=GenerateConfig(temperature=0.5) is not applied; the importer never reads task.config" (`benchmarks.py:4189-4191`) and its description (`:4114`). No such line exists for this row.
- **Where.** Ours: Task replay keeps only the Samples and the rendered prompt. No file on the replay or run path reads `task.config` (Checks run 8), so the Candidate answers with its own settings and no token cap. Theirs: `inspect_evals:agieval/utils.py:196`, `GenerateConfig(temperature=0, max_tokens=2048, top_p=1)`, applied by `inspect eval` to every Candidate call.
- **What differs.** inspect_evals asks greedily (temperature 0, top_p 1) and cuts every reply at 2,048 tokens. A cut-off reply loses its last `ANSWER:` line and scores 0 under `parse_answers`. Ours imposes neither the temperature nor the cap. So a long-reasoning Candidate can earn marks here that an inspect run would truncate away, and a sampled Candidate can answer differently from a greedy one.
- **Severity / bound.** `possibly-score-changing`, bound `unknown`. Every mark of a fixed reply is identical (answer sheets), so the gap lives entirely in what the Candidate writes, and only a paid run can measure it (Recommended paid runs). Its direction depends on the model: a cap only lowers inspect's score, while temperature can move it either way.

## Upstream notes

- **inspect_evals vs the original harness: a different examiner, `unbounded`.** [inspect_evals v0.20.0 `agie_sat_math`](https://github.com/UKGovernmentBEIS/inspect_evals/tree/v0.20.0/src/inspect_evals/agieval) departs from [ruixiangcui/AGIEval@84ab72d9](https://github.com/ruixiangcui/AGIEval/tree/84ab72d94318290aad2e4ec820d535a95a1f7552) on two grading dimensions. (1) **Prompt.** inspect_evals sends one user message, `Answer the following multiple choice question. … 'ANSWER: $LETTER' … LETTER is one of A,B,C,D.` with `A) option` lines (`inspect_evals:agieval/utils.py:68-76`). The harness sends `You are a helpful AI assistant.` as a system message (`fork:openai_api.py:88`), then `Q: <question> Answer Choices: (A)2 (B)4 …` ending `A: Among A through D, the answer is` (zero-shot) or `Let's think step by step.` (zero-shot CoT) (`fork:src/dataset_loader.py:25-35`, `:58-64`). It then makes a **second call** with the first reply and `Therefore, among A through E, the answer is` appended (`:250-277`). At this commit that second call goes to `gpt-35-turbo` whatever model answered first (`fork:run_prediction.py:196-197`). (2) **Answer extraction.** inspect_evals uses the `ANSWER:`-line regex (`inspect_ai:solver/_multiple_choice.py:98-108`). The harness takes the first capital letter A–F of the second-stage reply (`fork:src/post_process.py:72-78`, `:187-188`). On the sheets, a harness-style reply (` D.`, `(D)`, `The answer is (D).`) scores 1 under the harness and 0 under inspect on 220/220 Cases. An inspect-style `ANSWER: D` scores 1 under inspect and is credited by the harness only on the 52 Cases keyed A, because it reads the `A` of "ANSWER". The gap depends on what a Candidate writes, so it is `unbounded`. Sampling matches between the two: temperature 0 on both (`fork:openai_api.py:101`; `inspect_evals:agieval/utils.py:196`). The harness sets no token cap in the call; the paper says 2,048.
- **Harness vs paper.** The paper's CoT step 2 reads "[question] Explanation is: [explanation]. The answer is:" (`arxiv-src:sections/04_experiment.tex`, CoT subsection). The harness's v1.1 script appends `Therefore, among A through E, the answer is` (`fork:src/dataset_loader.py:255`, the "E" even on 4-option SAT-Math) and routes stage 2 to `gpt-35-turbo`. The harness wins, as recorded. It is also unknown whether the paper's 2023 GPT-4 numbers came from this 2024 v1.1 script: the README says "AGIEval-en datasets remain the same as Verison 1.0" (`fork:README.md:11`), and the data file is byte-identical, but the scripts were rewritten for v1.1 (`84ab72d 2024-06-13`).
