# Implement the generic Log seam

Prerequisite: review of [the spec](../spec/2026-09-09-OME-934-log-seam.md) and explicit implementation approval. Branch from updated origin/main after the docs PR merges. Reference the merged design rather than copying it into the implementation diff.

1. **Port and containment, test first.** Add `src/screamingface_engine/run_log_contract.py` and `runner/run_logs.py` under apps/screamingface-engine. Add focused behavior tests for factory/entry/exit failure, invalid records, immutable submission snapshots, expiry, off-thread emission and preservation of execution failure/cancellation. All absent/declining paths are silent.
2. **Existing bridge integration.** Add the app-local structured-Log input in `runner/executor.py`; share ordinary Log admission/eviction and map to existing LogData. Test ordering, root attachment, pressure/drop accounting, and unchanged Span/cost handling. Avoid a second queue or a new URL4/wire event.
3. **Execution lifecycle.** Inject the optional factory into Url4Executor and scope only url4_run, after world resolution and before bridge closure. Test teardown emission, result-serialization exclusion, early iterator close, cancellation, concurrent and nested runs. Preserve existing world cleanup.
4. **Composition proof.** Thread the optional factory through `runner/main.py::build_executor`, default None. A small fake adapter must produce a sequenced INFO Log through the public construction/lifecycle path. Do not wire a concrete Benchmark or model adapter. Add a layering regression asserting generic modules depend only on the port.
5. **Gates and review.** Run focused tests, then `uv run .claude/scripts/run_gates.py screamingface-engine` from the worktree root: append-only protection, Ruff lint/format, Pyright, layering, full pytest and coverage. Review failure precedence, expiry, trusted-callback limits and privacy. No live provider calls. Update the implementation ledger and task mirror, commit with Refs: OME-934 and open the code PR against main.

Reuse useful behavioral cases from closed PR 689 after adapting to current main. Do not cherry-pick its Benchmark claim machinery or PR 692's progress/discovery implementation. Existing tests remain unchanged. Implementation should stay in the Engine landing; any required change outside it is a scope decision.

The docs PR does not close OME-934. Complete the issue's close discipline only after the infrastructure implementation is reviewed, merged and verified. Producer/consumer work remains on its existing tickets.
