## 1. Problem

Stage E retired the Profile machinery (E1–E5c), but the review of 2026-10-29 confirmed debt in
three groups:

- **Behaviour.** The availability listing disagrees with chat (D17, L1). The Local Engine selects
  by a label rather than by the row chat uses (P-F2).

  the bootstrap-flag warning remain, though nothing writes or needs them.
- **Hygiene.** Dead code, Profile vocabulary, stale docs, a release lane that hides the Stage C/D
  breaking changes, and open records.

The epic cannot close until each item is either landed or explicitly ruled out of scope.

### 4.3 L4c — drop the `migration_note` column (RT-02)

- Migration `0016` removes the field.
- Under Tortoise 1.1.8, `RemoveField` on SQLite rebuilds the table (`remove_field` →
  `_remake_table`). The rebuilt table keeps the foreign-key references but **not**
  `unique_together` or the foreign-key indexes. It would silently drop the D1 uniqueness of
  `(account_id, provider)`.
- `0016` therefore restores the indexes on SQLite, as `0010` does (`_restore_sqlite_indexes`,
  `migrations/0010_simplify_request_cache.py:20-50`). The other option is to drop the plain column
  with `RunSQL` and remove it from state only. The choice is made at RED, against the pinning test.
- The upgrade fails closed if any `quarantined` or noted row exists. The downgrade re-adds a
  nullable column.
- The authoring note drops the autodetector's `OAuthConnection.account` proposal, as `0012`–`0015`
  do.

### 4.7 L7 — the Local Engine manages the Connection chat uses (P-F2)

Today the local adapter (`apps/screamingface-engine/src/screamingface_engine/connections/aigateway.py`)
works only on the row labelled `_MANAGED_LABEL = "screamingface"`:

- `:44`, and `_select` at `:253-259`;
- `list` at `:87-93`;
- `connect` at `:95-128`, `start_oauth` at `:130-145` and `disconnect` at `:147-166`.

Chat instead uses the migrated pair's effective row, or the single active row under the default
selector (L1). A user who connected through the gateway UI therefore reads `not_connected` locally
while chat works. With two active rows, one of them labelled `screamingface`, the user reads
`connected` while chat answers 409.

| Option | Read | Writes | Wire | Verdict |
|---|---|---|---|---|
| A. The gateway marks the effective row | each `/v1/oauth/connections` row gains a read-only `effective: bool`, computed by L1's selection function after the marker. The Engine selects that row; with no effective row, the status comes from `/v1/provider-access` | `connect` / `disconnect` address the effective row. With none, a create sends no label, so the gateway's unlabelled-write rule applies (`routes/oauth_connections.py:128-131,254-258`). Two or more active rows → `ConnectionConflict` | additive response field (`core/oauth/schemas.py:20-33`); OpenAPI changes (L9); one marker listing per call (`pair_authority.py:112-119`) | **recommended**: one rule, in the gateway |
| B. The Engine re-implements the rule | the Engine applies "one active row" itself | same as A | none | rejected: a second copy of the rule in another service. Wrong for a migrated pair whose reference is one of several active rows |
| C. Status only | status from `/v1/provider-access` | still label-addressed | none | rejected: disconnect can miss the row chat uses |

The hosted path (`mutable=False`) is unchanged. Option A's exact create and repair table is fixed in
the leaf's own spec before code. That table covers an `error` or `pending` row and the label
collision that a create with `screamingface` would hit. Version skew (a new Engine against an older
gateway with no `effective` field) is Q3.
