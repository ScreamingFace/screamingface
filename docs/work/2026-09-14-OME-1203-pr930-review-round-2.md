# OME-1203 — Close the PR #930 review round 2 findings

## Intent

PR #930 adds a standard metadata block beside every cached response and reports what the
cache saved. The second review round requested changes with seven findings. All seven were
checked against the code and all seven are real; CI is green, so these are uncovered edge
cases rather than failing tests. This unit closes them so the PR can be approved.

Two findings are the reason this is priority 2. Finding 3 makes the feature lie: before this
PR a retried, already-billed call under-reported spend as `0` silently, and the PR turns that
silence into a confident claim that the cache saved money which was in fact spent. Finding 6
leaves the published `url4` seam accepting negative amounts and unknown provenance strings
while its neighbouring value objects already reject out-of-vocabulary values.

## Test plan

Every test is a NEW function appended to an existing file or a new file — the append-only gate
forbids editing an existing test body.

- Migration: the trigger clears a stale block when `response_json` changes alone; leaves the
  block when both change together; never fires on a `hit_count`/`last_hit_at` bump; is absent
  on SQLite; is dropped on reverse. `ADD COLUMN` under a held conflicting lock fails within the
  timeout instead of queueing.
- Merge: under a concurrent fill committed between count and merge, `metadata_degraded` equals
  the rows actually degraded (real Postgres, `needs_postgres`).
- Retry: a transport retry whose second attempt hits reports `cache_status == "hit"`, no saved
  cost, and one `unpriced_hits`. A hit with no retry still prices normally.
- Precision: two maximum-precision amounts accumulate without rounding, at both run and span
  scope, and the two scopes agree on the exact value.
- url4: a negative amount is refused; an unknown provenance string is refused; both seams; the
  existing pairing tests still pass.
- Schema: `metadata_degraded` present in `schema.d.ts`.

- **Deviations:**
  - **Finding 2 (migration lock) took a review fix round.** `1438ffa2` shipped
    `Migration.atomic = False` plus a 5-attempt retry loop with backoff, so a lock-timeout
    failure could be retried. Ruling R10 caught that this let the downgrade's reverse operations
    commit in separate transactions — a crash between `AddMetadataColumn`'s reverse (drops the
    column, rebuilds the SQLite table) and the index-restore step could leave a database with
    both the column AND its indexes gone, worse than what 0011 replaced. `f6d39fb1` restored
    `atomic = True` and deleted the retry loop entirely: the DDL is now attempted exactly once
    under `SET LOCAL lock_timeout`, and a timeout fails the migration for the operator to rerun.
  - **Finding 1 (stale-metadata trigger) took a review fix round.** `56c964c6` shipped the
    trigger with plain `CREATE TRIGGER`, which is not idempotent the way `CREATE OR REPLACE
    FUNCTION` is — re-running migration 0011's forward SQL against an already-migrated table
    raised "trigger already exists," and the reverse (drop) path had no Postgres integration
    coverage at all. `943d98e0` switched to `CREATE OR REPLACE TRIGGER` (Postgres 14+) and added
    the missing forward→reverse coverage that caught the defect.
  - **Plan vs. shipped structure.** The retry demotion lives in
    `avoided_usd_for_outcome(aigw, cache)` in `runner/accounting.py`, not inline in the connector
    as the original plan described — the connector only produces the `retried` bit;
    `accounting.py` is the sole choke point that acts on it.
  - **Known gaps carried forward, not closed by this round:** PRD test 23 stays example-based
