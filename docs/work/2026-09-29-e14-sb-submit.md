# e14-sb-submit — SB-submit: submit with a receipt, name the system, cluster the result

## Intent

E14 (epic OME-1307), wave 3, unit SB-submit, in `apps/scoreboard`. `POST /v1/scores` gains the
clustered path behind `SCOREBOARD_CLUSTERING_ENABLED` (code default False): verify the gateway
cache-version receipt (C3, EdDSA JWS, PyJWT behind a port), resolve the system through the
registry (public boards, verified identity), cluster the run under one head as a `ReportedResult`,
and answer with `reported_result`, `reported_results_count` and `notices`. It also adds
`GET /v1/scores/{score_id}/results` (C10), the leaderboard count fields, the portal link, the pure
replay-access rule that SB-grants reuses, and per-app counters. No migration.
Plan (the full spec): `docs/plan/2026-09-29-e14-reproducible-submission/SB-submit.md`.
Build on branch `unit/SB-submit` (D1): no PR, no Linear issue, no merge gate.

## Security requirement of wave 2 (REGISTRY INPUT), and how it is met

`RegistryService.resolve_for_submit` takes `board_visibility` as an argument. The submit path owns the
revalidation, in two layers:

1. `ClusterStore._write` calls `ScoreStore.lock_visibility` (row lock, `_revalidate_visibility`)
   first inside the write transaction, before the registry or a head is read, so the `"public"` it
   passes is the state the transaction sees. Test: `test_a_board_that_turns_private_between_the_read_and_the_write_is_refused`
   (409, nothing written).
2. The route (`_cluster`) re-checks with `turned_private` before any public answer leaves, because
   the answer can carry another user's head (a run that joins a cluster, or an idempotent hit). Tests:
   `test_a_board_that_turns_private_before_the_answer_gives_no_public_data` (new head, joins another
   head, idempotent hit: 409 and no data in the body) and, for the results list,
   `test_results_list_of_a_board_that_turns_private_mid_read_gives_no_public_data` (the private 404).
   A private decision is not refused for being private (`test_a_private_board_answer_is_not_refused_for_being_private`).

Mutation checks (each reverted): removing the `turned_private` re-check, the `lock_visibility` call,
the server-side fingerprint overwrite, the `run_id=None` rule for an unreadable key, the receipt `sub`
check, the replay version check, the results-list re-check and the private-identity refusal each makes
a named test fail.

## Known limits and open items (recorded per the plan)

- G4 (open): backfill `0019` takes `run_id` from raw `metadata.run_id`; on a private board the key
  should be the scoped `sfp-` token. `0019` is not changed here.
- A NULL `benchmark_revision` escapes I-S1 (SB-schema OD-S4): two concurrent first submits on a
  board with no registered revision can make two heads. Accepted.
- Two concurrent first submits on a private board can make two heads (no unique key is possible).
  Accepted.
- A new head whose content hash equals a head already linked to another revision gives a second
  `IntegrityError` and so 409 `ConcurrentScoreUpdate`. Known limit.
- Step 3 edge: a `run_id` found but not readable by the caller goes on as a new submission and the
  new result is stored with `run_id=None`.
