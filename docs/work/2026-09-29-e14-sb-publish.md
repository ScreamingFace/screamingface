# e14-sb-publish — SB-publish: publish a cache version to GitHub, and admin takedown

## Intent

E14 (epic OME-1307), wave 4, unit SB-publish, in `apps/scoreboard`. The owner of a result publishes
its frozen cache version as a GitHub release (`POST /v1/results/{id}/publish`, C10). A background
worker leases the request, checks the bucket archive digest, and creates the release and its two
assets through the `ReleasePublisher` port (C7). An admin takes a publication down
(`POST /v1/admin/results/{id}/withdraw`), and the worker deletes the release and the tag. The core
is pure (state machine, eligibility, backoff, release body); GitHub and the bucket sit behind ports
with adapters. No migration.
Plan (the full spec): `docs/plan/2026-09-29-e14-reproducible-submission/SB-publish.md`.
Build on branch `unit/SB-publish` (D1): no PR, no Linear issue, no merge gate.

## Review round 1 fixes (2026-09-29, on branch `unit/SB-publish`)

Blocking findings, all fixed. RED first: five tests failed on the old code for the right reason
(attempts 0, no `last_error`, state published on a private board), then went green. Reverting the
two `src` files makes the same five fail again.

- **Cleanup loop with no sleep (findings 1 and 3, one defect).** `_cleanup` now calls
  `_retry_cleanup` for EVERY `PublisherError`: `record_retry` with `next_delay_s(job.attempts + 1)`.
  A cleanup has no attempt cap, so the row waits, counts the attempt and keeps `last_error`. The
  metric label is `retry` or `error` by `err.retryable`. `record_failed` is no longer called for a
  cleanup job. Tests: `test_a_final_error_in_a_cleanup_backs_off_and_records_the_error`
  (delete refused, and token mint refused): `next_attempt_at == now + 60 s`, `attempts == 1`,
  `last_error` set, the second `run_once` at the same clock returns False and makes no call.
  Known small case: when an admin withdraws a row during a publish, `finish_published` and
  `record_failed` still set `next_attempt_at = now` once, so the first cleanup pass runs at once;
  every error after that backs off.
- **Run-time board re-check (findings 2 and 4, one defect).** DECISION: added, on the strength of
  the stated PRD rule (Q6: private-board and gated-benchmark versions never go to the public repo).
  The orchestrator task text asked for the fix; finding 2 said to confirm it. Recorded here so the
  reviewer can veto it. `PublicationStore.revalidate_publishable(result_id)` reads the head's
  Benchmark fresh and returns `publish_refusal(...)` (`private_board` | `not_redistributable`), so
  the rule is one function (DRY). `PublishWorker._publish` calls it FIRST, before the archive read
  and before the publisher factory. A refusal ends in `record_failed(error=<code>)`, no GitHub call,
  metric `publish_attempts{result=error}`. A missing head or benchmark is refused as `private_board`
  (fail closed). The owner may publish again once the board qualifies (documented in
  `eligibility.py`; PB-E5 blocks only integrity errors). Tests: parametrized
  `test_a_board_that_stops_being_publishable_after_the_request_is_not_published` (the archive
  reader is empty, so a read before the check would show as `archive_missing`), and
  `test_the_owner_can_publish_again_when_the_board_is_publishable_again`.
  - Visibility-exit guard: no new row. The store method is named `revalidate_...`, which the guard
    treats as a revalidation by design, so `test_visibility_exit_guard.py` is unchanged.
  - Known limit: the read is not under a lock, so a flip during the upload window (seconds) is not
    caught. The route has the same limit; the window is now seconds and not hours.
- Findings believed wrong: none.
