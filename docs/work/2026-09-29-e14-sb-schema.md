# e14-sb-schema — scoreboard schema foundation for E14 (OME-1307), wave 1

## Intent

Add the storage that E14 (reproducible submissions) needs in `apps/scoreboard`: four new `Score`
columns, `Benchmark.redistributable`, five new tables (`system`, `system_revision`,
`reported_result`, `score_metadata_event`, `cache_version_publication`), two partial unique
indexes, and a backfill that gives every existing score one original `reported_result`. The
change is expand-only (safe for a rolling rollout) and adds no behavior: no route, store method
or portal file reads the new data. Plan: `docs/plan/2026-09-29-e14-reproducible-submission/SB-schema.md`.

- **Deviations:**
  - tortoise-dev companion skill waived by the user for E14 (2026-09-29); house patterns and the
    plan's exemplars were used instead.
  - 0018 keeps `source_field="head_id"`, `"replayed_from_id"`, `"pinned_baseline_id"` in its
    `CreateModel` (what the models serialize to) and then renames the three columns with one extra
    `RunSQL` (plan 5.2 lists no such op). WHY: Tortoise 1.1.8 rewrites a foreign key's
    `source_field` to the attribute name at init, so a hand-written `source_field="score_id"` in the
    migration made `makemigrations` propose an `AlterField` for each key on every run, and the
    `(head_id, submitted_at)` index was created on the non-existent column `head_id` (SQLite treats
    the unknown quoted name as a string literal, so it did not even fail). The rename gives the
    erd.md 2.2 column names, a correct index on `score_id`, and "No changes detected". SCH-7 now
    compares only the single-statement `RunSQL` ops (the two `CREATE UNIQUE INDEX`), because the
    renames are a tuple in one `RunSQL`.
  - `CacheVersionPublication` uses the plan 4.7 fallback: `id` UUID primary key plus a
    `OneToOneField` `result` (column `result_id`, unique). The one-to-one primary key worked in
    SCH-8, but Tortoise 1.1.8 does not round-trip it through migration state, so `makemigrations`
    kept proposing an `AlterModelOptions`. SB-publish should look rows up with `result_id=...` (works
    for both shapes).
  - Extra plan-local test `test_sch1b_migrations_reverse_and_reapply_cleanly` (reverse SQL of
    0018/0019 on SQLite, to 0017 not 0016: reversing an `AddField` on SQLite rebuilds `scores` and its
    DROP fails on a populated database, a Tortoise limit 0016 shares). SCH-1 also asserts the
    `reported_result` column names and the `score_id` index in the migration path.
  - Test helper `_migrated_to_legacy_head` applies `0004_add_run_cost_usd` after 0016: it is a leaf
    that no later migration depends on, so an explicit target of 0016 skips it and the seed would
    lack `run_cost_usd`. Production databases have it applied.
  - `tortoise_db` cannot run on PostgreSQL today (pre-existing: its sync schema fixture calls
    `asyncio.run` inside a running loop, also for `test_delete_scores.py`), so SCH-8/10/13 run on
    SQLite; the PostgreSQL index and constraint checks are in SCH-12.
  - `_metadata_run_id` also treats non-object metadata (a JSON list or string) as "no run_id".
- **Limits recorded (plan OD-S2, OD-S4):** `replayed_from` and `pinned_baseline` are RESTRICT, so
  `delete_scores` fails loudly for a score whose result another run replayed. A NULL
  `benchmark_revision` escapes the I-S1 partial index (both engines treat NULLs as distinct).
