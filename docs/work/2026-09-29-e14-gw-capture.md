# e14-gw-capture — the gateway call capture and the five E14 tables (OME-1307, E14b)

## Intent

Add the capture side of E14 reproducible submissions to `apps/aigateway`: the five E14 tables (one
migration, `0013_cache_versions`), the `core/cache_versions` package (ports, pure capture key and
record mapper, Tortoise adapter, in-process stats, orphan-prompt prune), and the chat-route hooks

## Open questions (the plan gives no default; STOP rule)

1. FK column name. The plan wants the column `cache_version_entry.blob_sha256` through `source_field="blob_sha256"` on the `blob` FK. In Tortoise 1.1.8 the autodetector always re-proposes `AlterField blob on CacheVersionEntry` for an FK with a custom `source_field` (the initialised model FK reports `source_field='blob_id'`). Two results: (a) the plan test `test_autodetector_proposes_no_cache_version_change` cannot pass; (b) the EXISTING test `tests/unit/test_migration_populated_db.py::test_autodetector_proposes_no_account_change` fails, because it pins the autodetector output to exactly `["Alter field account on OAuthConnection"]`. The generated migration also spelled `source_field='blob_id'`; that value would create a column that the model does not read. Option A: name the column `blob_id` (drop `source_field` on the model and in 0013). Both autodetector tests pass, no existing test edit, later units are not affected (GW-freeze and GW-replay use the attribute `blob_id` only). The column differs from erd 3.4 and plan section 5. Option B: keep `blob_sha256` and approve an edit of the existing test.
2. Existing test `tests/unit/test_migration_0012_provider_credential_slots.py::test_0012_downgrade_drops_only_the_marker_table` migrates to HEAD, then downgrades to 0011. Any new migration makes it drop the new tables too, so it fails after 0013. The fix is one line (`_tortoise(url, "migrate", "models", _MIGRATION)` instead of `_tortoise(url, "migrate")`). Rule 5 and the append-only gate forbid the edit without approval.

- Blast radius: `routes/chat.py` body is re-indented under one `try`; statement order is unchanged. Every existing chat route test passes.
