# e14-gw-capture — the gateway call capture and the five E14 tables (OME-1307, E14b)

## Intent

Add the capture side of E14 reproducible submissions to `apps/aigateway`: the five E14 tables (one
migration, `0013_cache_versions`), the `core/cache_versions` package (ports, pure capture key and
record mapper, Tortoise adapter, in-process stats, orphan-prompt prune), and the chat-route hooks
that write one `cache_capture_entry` row for each traced call. A capture failure never changes the
chat response. The plan is `docs/plan/2026-09-29-e14-reproducible-submission/GW-capture.md`.

## Wisdom review

- Schema touched: migration 0013 is in the same iteration as the models (S1).
- No bare `except`. The two `except Exception` clauses are the plan's never-raise boundaries (`begin_capture`, `record_capture`, `build_capture_key`) and the route error hook, which re-raises.
- Typecheck clean with no new `# type: ignore` in `src`; the two Postgres test files copy the existing `# type: ignore[import-untyped]` for `asyncpg` and `testcontainers`.
- Security: no prompt, response, key material or full key hash is logged (type name and 8-char trace prefix, 12-char key prefix only). The prompt is stored in plaintext by design (erd 3.1); DEPLOYMENT.md says so. No credential, `ORMStore`, keychain or `AIGATEWAY_SECRET_KEY` touch.
- Known limit (plan-literal): `record_capture` for `hit` and `stored` runs BEFORE `attach_hit_metadata` / `attach_success_metadata`. If one of those raised, the call would also get an `error` row (two rows for one call). The plan fixes this order; it was not changed.
- Known limit: a prompt has no size cap in v1 (plan section 7.1). The live cache caps the response only.
- Blast radius: `routes/chat.py` body is re-indented under one `try`; statement order is unchanged. Every existing chat route test passes.
