# e14-sb-grants — SB-grants: issue replay grants from a pin

## Intent

E14 (epic OME-1307), wave 4, unit SB-grants, in `apps/scoreboard`. `POST /v1/replay-grants` (C6,
scoreboard side) turns a pin (`result:<uuid>`, `score:<uuid>`, `name`, `name@r<N>`, `name@<date>`)
plus a `benchmark_id` into ONE result, applies the replay access rule (`core/replay_access.py`) and
signs a short EdDSA grant (`iss=scoreboard`, `aud=aigateway`, `sub`, `vid`, `rid`, `iat`, `exp=iat+12h`)
that the gateway checks (GW-replay). The route is read-only. Nothing is signed for a pin that does
not resolve. Identity follows D5 (`cloudflare_headers` in production: verified email or 401 / 403;
`disabled` is a dev fallback with `sub = "anonymous"`).
Plan (the full spec): `docs/plan/2026-09-29-e14-reproducible-submission/SB-grants.md`.
Build on branch `unit/SB-grants` (D1): no PR, no Linear issue, no merge gate.

## Known limits (recorded)

- **Visibility flip inside one request.** `ReplayPinResolver.resolve` reads the board row once and
  uses it for every access decision of the scan. A public -> private flip inside that one request
  could still give a non-owner a grant. It is NOT re-checked with `turned_private` (the get_score
  pattern), because the grant carries only ids, is bound to the caller (`sub`), names one cache
  version, and the gateway serves that version only. This is the approved guard-row exception, not
  a guard. If the orchestrator wants it closed, the fix is one fresh visibility read after the
  scan that turns a non-owner's `allow` into `PinNotFound`; that changes behaviour, so it was not
  done here.
- **Grant life 12 h** (D4): a grant can expire during a long run (`GRANT_TTL_S` docstring,
  `DEPLOYMENT.md`).
- Equivalent mutant: forcing `identity_verified=True` in the route changes no test, because in
  `disabled` mode `write_identity` gives `None`, and a `None` caller is never an owner.
